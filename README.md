# TaleForge — 모듈화 버전

기존 11만 6천 줄짜리 `taleforge.html` 파일 하나를 **298개의 작은 파일**로 나눴습니다.
게임 동작은 이전과 완전히 동일합니다 (실제 브라우저로 원본과 1:1 비교 검증 완료 — 2574개 함수 전부 일치, 오류 0건).

## 이번 정리 작업 (Cleanup pass)

파일을 나눈 뒤, 코드 전체를 다시 스캔해서 안 쓰는 코드를 정리했습니다.

- **진짜 안 쓰는 코드 141개 삭제**: 대부분 "환생 시 초기화" 계열의 헬퍼 함수였는데, 확인해보니 실제로는
  삭제해도 되는 게 맞았습니다 — 해당 데이터들은 애초에 "회차를 넘어 계속 누적되어야 하는" 기록(업적률,
  나비효과 지수, 전설 조각 등)이라 환생할 때 지우면 오히려 안 되는 것들이었고, 완전 초기화(새 게임)는
  `clearAllGameData()`가 키 접두사로 한 번에 처리하고 있어서 이 함수들 자체가 처음부터 불필요했습니다.
- **의도적으로 남겨둔 것**: `SHIP_KEY`(구버전 세이브 호환용이라고 원 코드에 주석으로 명시됨),
  `BLOODLINE_KEY`/`BL_V2_KEY`(두 시스템을 하나의 저장 키로 통합하겠다는 의도적인 설계로 확인됨),
  `LOOP_REC_KEY`(이미 있던 `LOOP_RECORD_KEY`와 같은 값을 가리키는 중복 상수지만, 실제로 쓰이고
  있어서 안전하게 통합할 방법을 찾지 못해 그대로 뒀습니다)는 건드리지 않았습니다.

## 나누는 도구 자체에서 발견해 고친 버그

정리하다가 이 게임 코드 자체의 특징 하나를 발견했습니다 — 같은 함수 이름을 **여러 군데서 순차적으로
"덧씌우는"(몬키패치) 패턴**이 굉장히 많이 쓰입니다 (예: AI에게 보내는 프롬프트를 조립하는
`buildLightSystem`은 무려 21곳에서 덧씌워집니다). 원본 파일에서는 "나중에 나오는 코드가 이긴다"는
단순한 규칙으로 항상 올바른 순서가 보장됐는데, 파일을 여러 개로 쪼개고 나면 "어느 파일이 브라우저에서
먼저 실행되는가"가 원본의 줄 순서와 100% 같지 않을 수 있다는 걸 발견했습니다.

실제로 이것 때문에 `checkBossSpawn`(회차 보정 로직), `fulfillProphecy`(예언 실현 처리),
`wmSwitchTab` 등 몇몇 함수가 **덧씌워지는 순서가 뒤바뀌어서 최신 로직 대신 예전 버전이 실행되는**
문제를 실제로 찾아냈고, 나누는 도구(`tools/generate.js`) 자체를 고쳐서 "같은 이름을 덧씌우는 코드는
항상 원본과 같은 순서로 실행되도록" 보장하게 만들었습니다. 이후 21곳에서 덧씌워지는 `buildLightSystem`을
포함해 관련된 모든 함수를 브라우저로 직접 열어 원본과 실제 실행 결과가 같은지 하나하나 대조 확인했습니다.

같은 정리 과정에서 나누는 도구 자체의 버그 두 개를 더 찾았습니다:
- **빌드 스크립트의 문자열 치환 버그**: 최종 파일을 합치는 `build.js`가 코드 전체를 한 번에 끼워 넣는
  방식이 JS의 특수 치환 패턴(`$&` 등)과 우연히 충돌해서, 게임 코드 안의 정규식 치환 로직 3곳이 미묘하게
  깨져 있었습니다. 안전한 방식으로 고쳐서 재확인했습니다.
- **재할당되는 값의 연결 누락**: `let X = ...`로 선언된 뒤 나중에 `X = 새값`처럼 다시 대입되는 값들 중
  일부(`_embeddedKeys` 등 API 키 저장 관련 값 포함)가, 재대입되는 부분만 다른 파일에서 안 보이게
  누락되는 버그가 있었습니다. API 키 추가 기능을 실제로 눌러서 정상 작동하는 것까지 확인했습니다.

## 데이터 분리 (data/ 폴더)

로직이 전혀 없는 "그냥 표"에 가까운 것들 — 몬스터/아이템/스킬/업적 정의처럼 숫자·텍스트만 나열된 것 —
을 함수 코드와 분리해서 `data/` 폴더로 뺐습니다 (127개 파일). 이제 "몬스터 하나 추가", "아이템 밸런스
수치 조정" 같은 작업은 로직이 전혀 없는 데이터 파일만 만지면 됩니다. 어떤 걸 데이터로 판단할지는 자동으로
분석했습니다 (함수 호출이나 실행 로직이 전혀 없이 순수하게 값만 나열된 경우만 — 애매하면 안전하게
로직 쪽에 남겨뒀습니다), 브라우저 대조 검증도 다시 통과했습니다.

## 공통 유틸리티 (utils.js)

`$`(엘리먼트 찾기), `esc`(HTML 이스케이프), `toast`(알림), `lsGet`/`lsSet`/`lsDel`(저장소
읽기/쓰기), `dbGet`/`dbSet`(저장소 위에 JSON 직렬화를 얹은 얇은 래퍼) — 특정 게임 시스템과 무관하게
전체에서 두루 쓰이는 8개를 `src/utils.js` 하나로 모았습니다. 자동으로 "많이 쓰이는 것"만 기준으로 뺀 게
아니라, 하나하나 내용을 직접 확인해서 게임 상태(`S`)나 특정 시스템에 대한 의존이 전혀 없는 것만
골랐습니다 (예: `loadCycleCount`처럼 여러 곳에서 쓰여도 회차 시스템 자체에 속하는 건 유틸이 아니라고
보고 제외했습니다). 대조 검증도 다시 통과했습니다.

## 위치 인식 콘텐츠 배치 (보스 / 몬스터)

기존에는 보스가 "N턴이 지나면 어디에 있든 무조건 등장"하는 방식이었고, 돌발 조우(랜덤 인카운터)
몬스터도 장소와 무관하게 고정된 하나의 풀에서 뽑혔습니다. 실제 플레이 중이라면 마을 한복판에서
갑자기 고대 드래곤이 나타나는 식이라 어색했습니다. 이미 게임에 있던 "장소 유형별 상주 NPC"
시스템(`LOC_NPC_POOL`/`getOrAssignLocNpcs` — 마을/도시/던전/성소마다 다른 NPC가 배치되는 방식)과
같은 원리를 보스와 몬스터에도 적용했습니다.

- **보스 (`data/054-이동수단-시스템.js`의 `BOSS_MONSTERS`, `misc/054`의 `checkBossSpawn`)**:
  각 보스에 `locTypes`(예: `['dungeon','event','special']`)를 추가했습니다. `turnTrigger`(턴 수)는
  이제 "이 시점부터 등장 가능"이라는 조건일 뿐이고, 실제 등장은 플레이어가 그 보스에 맞는 장소 유형에
  실제로 들어섰을 때 일어납니다 — 안전 지역(마을·도시·수도)에 있는 동안은 대기하다가, 던전이나
  사건 지역에 들어서는 순간 등장합니다. `locTypes`가 없는 보스(다른 시나리오용)는 기존처럼 장소
  무관하게 등장해 하위 호환을 유지합니다.
- **랜덤 인카운터 몬스터 (`data/053-게시판-시스템.js`의 `LOC_MONSTER_POOL`, `quest/086`의
  `checkRandomEncounter`)**: 기존에도 "이 장소에서 실제로 AI가 서술해 등장했던 몬스터 기록"을
  60% 확률로 최우선 사용하는 로직은 있었는데(가장 그 장소다운 선택이라 그대로 유지했습니다), 그
  기록이 없을 때 쓰던 폴백이 장소 무관 고정 풀 하나뿐이었습니다. 이제 그 폴백을 장소 "유형"별
  몬스터 풀(`LOC_MONSTER_POOL` — 던전엔 해골·구울·골렘, 성소엔 타락한 사도·망령, 마을 근처엔
  들개·좀도둑 등)로 교체했습니다. AI 호출 없이도 장소에 안 맞는 몬스터가 나올 확률이 크게 줄어듭니다.
- 두 기능 모두 실제 빌드된 `dist/taleforge.html`을 헤드리스 브라우저로 열어 직접 검증했습니다:
  마을에 있을 때는 보스가 대기하다가 던전으로 이동하자 즉시 등장했고, 던전/성소에서 각각 그 장소
  유형에 맞는 몬스터(해골 전사 / 타락한 사도)가 실제로 스폰되는 것을 확인했습니다.

## 장소별 레벨대 (요즘 다른 게임들처럼)

기존엔 장소 자체에 "어울리는 레벨"이라는 개념이 아예 없었습니다 — 몬스터 스탯이 오직 "그 순간 보고 있는 플레이어의 레벨"에서만 계산돼서, 같은 이름의 몬스터(예: "토끼")가 레벨 1이 만나면 레벨 1짜리로, 레벨 80이 만나면 레벨 80짜리로 나오는 식이었습니다. 장소에 정체성이 없었던 거죠.

- **`getLocationLevelBand(loc)`** (`world/052-동대륙-추가-장소-4.js`): 이 장소에서 만나는 몬스터의 레벨대(`[최소, 최대]`, **폭은 항상 2** — 한 장소 안에서 몬스터 레벨 차이가 최대 1~2밖에 안 나도록)를 돌려줍니다.
  1. 먼저 장소 "유형"(`loc.type`: 마을/도시/수도 등, 항상 존재) 또는 `dangerLevel`(1~6, 주로 던전류)로 그 유형이 게임 전체에서 대략 걸쳐 있는 **넓은 범위**(envelope)를 정하고 — 예: 마을 5~20, 수도 50~100.
  2. 그 장소 고유의 id/이름을 시드로 삼아, 그 넓은 범위 "안"에서 이 장소만의 **좁은 2레벨 구간**을 하나 결정적으로(같은 장소는 언제 다시 방문해도 항상 같은 구간) 골라 고정합니다.
  이렇게 하면 같은 "마을" 유형이어도 마을마다 서로 다른 레벨대(예: A마을 10~12, B마을 14~16)를 갖고, 105개 장소 전부에 손으로 새 필드를 매길 필요가 없습니다. 헤드리스 브라우저로 직접 검증했습니다 — 같은 장소는 몇 번을 조회해도 항상 같은 레벨대, 다른 장소는 서로 다른 레벨대, 폭은 항상 정확히 2.
- **몬스터 스탯**: `autoDetectAndRegisterEnemy`(AI 서술문에서 적을 자동 등록하는 로직)가 이제 두 신호를 분리해서 씁니다 — 이름 자체의 상대적 세기는 이미 있는 `MONSTER_TIER_TABLE`(예: 슬라임=극하급, 늑대=그보다 위 등급, 이름마다 고정)로 정하고, 장소의 레벨대는 그 위에 곱해지는 "이 구역 전체의 배율"만 담당합니다. 그래서 같은 장소 안에서도 슬라임과 늑대는 여전히 서로 다른 세기를 유지하면서(늑대가 항상 더 강함), 장소를 옮기면 둘 다 그 장소 수준에 맞게 함께 오르내립니다 — 헤드리스 브라우저로 확인: 마을에서는 슬라임 HP62·늑대 HP128, 수도로 옮기면 슬라임 HP60·늑대 HP112로, 슬라임<늑대 관계는 항상 유지됩니다.
- **범죄/체포 시스템**: 지명수배(무법자) 상태에서 도시·마을·수도를 돌아다닐 때 경비병에게 발각되는 확률(`checkArrestCondition`, `quest/086`)이, 캐릭터 레벨이 그 장소의 적정 레벨대보다 많이 낮으면 크게 올라갑니다 — 강제로 막는 게 아니라 "이 도시에서 나쁜 짓 하기엔 아직 약하다"는 게 자연스럽게 체감되도록 발각률과 마주치는 경비대 등급을 높이는 방식입니다. 직접 테스트한 결과, 저레벨 무법자가 고레벨대 장소에서는 약 88% 확률로 발각됐고, 그 장소 레벨대에 맞는 캐릭터는 약 10%로 뚝 떨어졌습니다.
- **AI 프롬프트**: 시스템 프롬프트에도 "이 장소의 적정 레벨대: Lv.X~Y" 힌트를 추가해서, 격차가 크면 AI가 서사에서도 위축감/여유로움을 자연스럽게 반영하도록 유도합니다.

## 생태계 시스템 + 기존 시스템 통합 + "이상 현상" 하드코딩

"게임이 살아있다는 느낌"을 위해 세 가지를 한 번에 진행했습니다 — 새로 만들기, 예전에 따로 놀던 시스템 정리, 그리고 AI 서술에만 의존하던 부분을 실제로 작동하게 하드코딩하는 것.

### 1) 여러 곳에 따로 있던 "적 강도 계산"을 하나로 통합

전에는 적 강도를 정하는 공식이 `getEnemyScaleMultiplier`(dangerLevel 직접 계산), `autoDetectAndRegisterEnemy`(자체 계산), AI 프롬프트 안의 별도 키워드 추측 시스템 — 이렇게 세 군데서 각자 다른 숫자를 말하고 있었습니다. **`getLocationPowerScale(loc)`**(`world/052`) 하나로 통일해서, 이제 이 세 곳(그리고 `checkRandomEncounter`, `checkBossSpawn`)이 전부 같은 기준으로 계산합니다. 헤드리스 브라우저로 확인: 같은 장소에 대해 `getEnemyScaleMultiplier().dangerMult`와 `getLocationPowerScale()`이 정확히 같은 값을 냅니다.

### 2) 생태계(개체수 + 포식 관계)

`world/052`에 새 저장소(`tf-loc-ecosystem`, `loadLocEco`/`saveLocEco`)를 만들어서, 장소별로 몬스터 이름마다 "개체수"(0~100)를 추적합니다.
- **회복**: 시간이 지나면 등급별 평형치를 향해 서서히 회복됩니다(약한 개체는 빠르게, 강한 포식자는 느리게) — `tickLocEcosystem`.
- **사냥의 영향**: 잡으면 그 이름의 개체수가 줄고, 그보다 약한 등급(먹이 관계상 하위)은 포식 압박이 줄어 소폭 늘어납니다 — `onLocMonsterKilled`. 몬스터가 죽는 경로 3곳(AI 판정, 스킬 즉사) 전부에서 공통으로 호출되는 `autoDropLootOnDeath`에 연결해서 어디서 죽든 빠짐없이 반영됩니다.
- **조우 확률**: 랜덤 인카운터(`checkRandomEncounter`)가 이제 균등 랜덤이 아니라 그 장소의 현재 개체수에 비례해서 몬스터를 뽑습니다(`pickWeightedLocEcoName`) — 많이 사냥한 종은 뜸해지고, 안 건드린 종은 더 자주 나옵니다.
- 전부 `loc.id` 기준으로 저장되므로 AI가 즉석에서 만든 장소든 원래 있던 105개든 구분 없이 자동으로 적용됩니다.

### 3) "이상 현상"(장소 레벨 무시) — AI 서술 의존 → 실제 하드코딩

예전엔 "필드에 안 어울리는 고레벨 몬스터가 나타난다"거나 "고룡이 마을을 덮친다"는 게 전부 AI 프롬프트 지침으로만 있었고, 실제로 죽는지 사는지 판정하는 코드가 없었습니다. API 없이 하드코딩하면 이 부분은 통째로 사라지는 셈이었습니다.

- **`pickTierNameSample(tierMin, tierMax)`**(`quest/086`): `MONSTER_TIER_TABLE`의 최상위 등급(10~13 — 신화급/상급마물/전설급, 전부 `solitary`라 원래도 "개체수" 없이 단독 희귀 존재로 설계돼 있었습니다)에서 실제 이름과 스탯을 뽑아줍니다.
- **필드 이상 현상**: `checkRandomEncounter`에 장소 위험도와 완전히 무관한 아주 낮은 확률(턴당 0.15%, 평균 약 670턴에 1번)의 별도 판정을 추가했습니다. 걸리면 그 장소 레벨대를 무시한 진짜 몬스터가(실제 HP/공격력 포함) 등장합니다.
- **재앙(`CATASTROPHE_POOL`, `checkCatastropheEvent`)**: 이제 실제 대상 장소를 고릅니다(플레이어가 지금 정착지에 있으면 그곳 우선, 아니면 무작위 정착지). **플레이어가 하필 그 자리에 있으면 진짜 전투가 벌어지고**(11~13등급에서 샘플링), 그 장소의 생태계 개체수도 크게 줄어듭니다(재앙이 휩쓸고 간 자리는 나중에 가도 한동안 몬스터가 뜸합니다) — 자리에 없었다면 기존처럼 배경 서사로만 남습니다.
- **생존 → 이야기로 남음**: 이상 현상이나 재앙급 몬스터를 실제로 물리치면 `anomaly_survivor`/`catastrophe_survivor` 업적이 해금되고 타임라인에 영구 기록됩니다 — "죽을 뻔했는데 살아남았다"가 그냥 흘러가는 서술이 아니라 실제로 남는 기록이 됩니다.

전부 헤드리스 브라우저로 직접 실행해서 확인했습니다: 개체수가 사냥에 따라 실제로 오르내리고, 가중치 추첨이 흔한 개체를 훨씬 자주 뽑고, 이상 현상 발동 시 진짜 강한 몬스터가 등록되고, 그걸 물리치면 업적이 실제로 해금되는 것까지 전부 확인했습니다.

## 자동플레이 — 사람 없이도 끝까지 스스로 돌아가게

원래 있던 자동플레이 도구(`misc/279-AUTO-PLAY-SYSTEM.js`)는 화면에 뜬 선택지 중 하나를 골라 실제로 `sendMsg()`를 호출하는 방식이라 "실제로 플레이하듯이" 데이터를 쌓기에 정확히 맞는 도구였습니다. 근데 확인해보니 선택지 목록 밖에 있는 별도 팝업/화면 네 가지에서 막히는 문제가 있었습니다 — 전부 자동플레이가 못 보는 곳에서 사람이 직접 버튼을 눌러야만 진행되던 부분입니다.

- **스탯 미배분** — 레벨업 때 받는 스탯 포인트는 `+`/`+5` 버튼을 직접 눌러야 배분되는데, 자동플레이는 선택지만 보기 때문에 포인트가 계속 쌓이기만 하고 안 쓰였습니다. → 포인트가 남아있으면 매번 무작위 스탯에 1씩 자동 배분하도록 추가했습니다(`STAT_POINT_ALLOC_KEYS` 기준 — 배분 불가능한 파생 스탯은 제외).
- **전직 제안 팝업** — 조건을 채워도 "발견됨"으로만 기록되고, 실제 전직은 별도 팝업의 "⚡ 전직" 버튼을 눌러야만 일어났습니다. → `job-suggest-popup`/`wanderer-evo-popup` 둘 중 뭐가 뜨든 첫 번째 선택지를 자동으로 수락하게 했습니다.
- **퀘스트 수락 팝업** — AI가 자동 생성한 퀘스트도 별도 팝업의 수락 버튼을 눌러야만 실제로 수락됐습니다. → `window._qapPending`이 있으면 자동으로 수락합니다.
- **환생(게임오버 후)** — 캐릭터가 죽으면 자동플레이가 그냥 멈췄습니다(사람이 "환생하기"를 눌러줘야 재개). → 게임오버 화면이 뜨면 자동으로 환생 화면으로 넘어가고, "환생 시작" 버튼도 자동으로 눌러서 계속 이어지게 했습니다.

전부 헤드리스 브라우저로 직접 확인했습니다 — 스탯 배분(50→53, 포인트 5→4, 저장소도 동기화됨), 전직 팝업 자동 수락, 게임오버→환생 트리거까지 실제로 작동하는 것을 검증했습니다.

## 게임 전체 학습 시스템 — 겪을수록 자동으로 성숙해짐

기존에 있던 `predictCombatStateFromLearning`(전투 중이냐 아니냐를 과거 패턴으로 자동 예측)의 패턴을 게임 전체로 넓혔습니다. `quest/086`에 `getSituationBucketKey`/`recordSituationExample`/`pickLearnedSituationExample`을 새로 추가했습니다.

- **상황 버킷**: `사건 종류 + 장소 유형 + 몬스터 등급`으로 상황을 분류합니다(예: `anomaly|village|high`). 이 게임에 이미 있는 장소 레벨대·몬스터 등급 체계를 그대로 재사용합니다.
- **자동 축적**: 시스템이 트리거하는 사건(돌발 조우의 이상 현상, 보스 등장, 재앙)이 벌어지면, 그 사건을 AI가 실제로 어떻게 서술했는지가 자동으로 해당 버킷에 쌓입니다(이미 있던 `tf-narrative-log` 기록 지점에 훅을 걸었습니다) — 사람이 손댈 게 없습니다.
- **자동 재사용**: 한 버킷에 예시가 15건 이상 쌓이면, 다음부터 같은 종류의 사건이 벌어질 때 AI에게 새로 서술을 요청하는 대신 쌓인 예시 중 하나를 재사용합니다. 이름이 다르면(예: 예시는 "검은 늑대"였는데 이번엔 다른 몬스터) 문장 속 이름만 안전하게 바꿔치기합니다.
- 흔한 조합(예: 마을 근처 조우)은 금방 성숙해서 빨리 재사용되고, 희귀한 조합(예: 수도의 최상급 이상 현상)은 오래 걸립니다 — "많이 겪은 만큼 그 부분은 저절로 성숙해진다"는 게 자동으로 일어납니다.

**정직하게 짚어드릴 부분**: 이건 그 사건의 서술 문장을 AI가 새로 지어내는 대신 재사용하게 해서 **일관성을 높이고 AI가 창작해야 할 부담을 줄이는** 효과가 있습니다. 다만 이 4곳(돌발 이상 현상·보스 등장·재앙)은 전부 플레이어의 원래 턴에 묻어가는 프롬프트 힌트라, 그 턴의 AI 호출 자체는(플레이어 행동에 응답은 해야 하니) 어차피 일어납니다 — 그러니까 **API 호출 횟수 자체를 줄이는 효과는 아직 없고**, 호출 내용의 품질/일관성을 높이는 효과입니다.

## 독립 호출도 학습시키기 — 이번엔 진짜로 API 호출 횟수가 줄어듭니다

위 상황-학습 시스템은 "플레이어 턴에 묻어가는" 서술문만 재사용했습니다. 이번엔 그 반대 — `generateAILocation`(새 장소 발견)과 `generateAIQuest`(AI 퀘스트 생성)처럼, **함수가 실행되는 것 자체가 독립적인 API 호출 1건**인 곳에 같은 패턴을 적용했습니다. 여기서 예전 결과를 재사용하면 그 턴은 AI를 아예 부르지 않습니다.

- `quest/086`에 `OBJECT_LEARN_KEY`(`loadObjectLearnDB`/`saveObjectLearnDB`/`recordGeneratedObject`/`pickGeneratedObject`/`getObjectLearnStats`)를 새로 추가했습니다. 상황-학습이 "문장"을 쌓는다면, 이건 "완성된 결과 객체"(장소 전체, 퀘스트 전체)를 통째로 쌓습니다.
- **장소 생성** (`quest/229`의 `generateAILocation`): 트리거 종류(턴 수·NPC 이름 등 매번 달라지는 부분은 잘라내고 "재료 산지 제보", "자동 세계 확장" 같은 종류만 남깁니다) + 세계관 + 현재 장소 유형으로 버킷을 만듭니다. 같은 버킷에 12건 이상 쌓이면, AI를 부르지 않고 예전에 만든 장소 중 하나를 새 ID로 복제해서 그대로 씁니다.
- **퀘스트 생성** (`job/087`의 `generateAIQuest`): 등급(S/A/B/C/D) + 상황 종류 + 세계관으로 버킷을 만듭니다. 마찬가지로 12건 이상 쌓이면 예전 퀘스트 내용(제목·설명·보상·완료조건 등)을 재사용하고, id·상태·타임스탬프만 새로 부여합니다. 재사용된 퀘스트도 기존과 똑같은 수락 팝업(`showQuestAcceptPopup`)을 거치므로, 자동플레이의 퀘스트 자동수락 기능과도 그대로 호환됩니다.
- 두 경우 다 이미 알려진 이름과 겹치면(장소는 `isLocationAlreadyKnown`, 퀘스트는 기존 퀘스트 제목 목록) 재사용을 건너뛰고 정상적으로 AI를 새로 부릅니다 — 재사용이 오히려 "이미 있는 걸 또 만드는" 부자연스러운 상황을 만들지 않도록 한 안전장치입니다.
- 헤드리스 브라우저로 두 함수 모두 검증했습니다: 버킷이 성숙하지 않았을 때는 정상적으로 AI 호출 경로로 진입하고, 12건 이상 쌓인 뒤에는 `callGeminiDirect`가 전혀 호출되지 않은 채로 재사용된 장소/퀘스트가 정확히 반환·팝업되는 것을 확인했습니다.

**부수적으로 발견하고 고친 버그**: 이 작업을 검증하던 중 `window.getAllLocations()`가 초기화 이후 항상 예외를 던지는 기존 버그를 발견했습니다 — `quest/229`가 "원래 장소 목록 함수"를 참조로 저장해두는 시점이 실제로 그 함수가 준비되기 *전*이라, 항상 `undefined`를 붙잡고 있었습니다(모듈 파일에 이미 있던 "지연 실행" 주석에 정확히 설명된 유형의 순서 문제입니다). 그 결과 `isLocationAlreadyKnown`, `generateAILocation`을 포함해 게임 전체에서 장소 목록을 쓰는 모든 곳이 게임이 다 로드된 뒤부터는 조용히 실패하고 있었습니다 — 화면에 에러가 안 뜨니 눈치채기 어려운 버그였습니다. 참조를 잡는 시점을 올바른 위치로 옮겨서 고쳤고, 고친 뒤 실제로 98개 장소가 정상적으로 반환되는 것을 확인했습니다.

## 독립 호출 전부 훑어서 안전한 곳엔 다 적용

"이왕 하는거 다 하는 게 좋지 않냐"는 요청으로, `callGeminiDirect`를 부르는 독립 호출 함수를 전부(약 20곳) 찾아 하나씩 검토했습니다. 안전하게 재사용해도 되는 곳엔 전부 같은 학습-재사용 패턴을 적용했고, 재사용하면 오히려 이상해지는 곳은 의도적으로 건드리지 않았습니다 — 아래에 둘 다 정리합니다.

**이번에 새로 적용한 곳**:
- **아이템 생성** (`items/006`의 `generateAIItem`, `items/007`의 `generateItemBatch`): 슬롯+세계관+직업+종족+레벨대(10단위)로 버킷화. `generateItemBatch`는 배치 전체(요청 개수만큼)가 재사용 가능할 때만 AI 호출을 생략합니다. 참고로 `items/007`엔 원래도 "무제한 영구 캐시"가 있었지만, 그건 만들어진 아이템을 나중에 잃어버리지 않게 저장만 해둘 뿐 새로 만들 때 API 호출을 생략해주진 않았습니다 — 이번에 그 부분을 실제로 채웠습니다.
- **던전 방 생성** (`combat/256`의 `generateDungeonRoom`): 등급+테마+강제방유형(보스 등)+층 밴드(3층 단위)로 버킷화. 단, 이 던전이 원래 등급보다 훨씬 강한 존재였다는 걸 그 순간에 드러내는 "이변" 이벤트가 터진 방은 재사용 대상에서 제외했습니다 — 그 반전은 그 순간에만 의미가 있어서 미리 쌓인 문장을 재사용하면 어색해집니다.
- **던전 행동 결과 생성** (`combat/256`의 `generateDungeonChoiceResult`): 방 유형+성공등급(대성공/성공/실패/대실패)+사용 스탯+던전 등급으로 버킷화.
- **경매 목록 생성** (`misc/314`의 `generateAuction`): 세계관으로 버킷화.
- **예언 생성** (`lore/301`의 `generateProphecy`): 종족+직업으로 버킷화. 예언은 원래도 "모호하고 시적으로" 짓게 되어 있어 이름이 문장에 직접 박히지 않으므로 재사용에 특히 안전합니다.
- **자동 전직 제안 통합** (`race/064`의 `autoSuggestNextJob`): 이건 캐시를 새로 만든 게 아니라 **버그를 고친** 쪽에 가깝습니다 — `job/042`의 수동 "✨ AI 직업 탐색" 버튼은 이미 "이 부모 직업에서 한 번 파생시킨 적 있으면 영구 재사용"하는 자체 캐시(`AI_JOB_POOL`)가 있었는데, 자동으로 뜨는 전직 제안 경로는 그 캐시를 전혀 조회·기록하지 않아서 같은 부모 직업도 매번 새로 API를 부르고, 두 경로의 직업 계보가 서로 다르게 갈라지는 불일치가 있었습니다. 이제 같은 캐시를 공유합니다.

**정직하게 짚어드릴 부분 — `generateDungeonChoiceResult`만 다른 트레이드오프**: 위 상황-학습 시스템(보스·이상현상·재앙)과 똑같이, 방의 정확한 디테일(`room.description`)을 그대로 지칭하진 않는 "행동 결과 묘사"라 재사용해도 완전히 이 방에 맞춘 문장은 아닙니다. 다른 항목들은 재사용된 내용이 애초에 특정 순간을 안 가리키게 설계돼 있어(아이템 이름, 던전 방 묘사, 경매 목록, 예언 등) 이 트레이드오프가 없습니다.

**의도적으로 건드리지 않은 곳**: 아래는 입력이 "이번에 실제로 일어난 구체적 사건/텍스트"라서, 캐시로 예전 결과를 재사용하면 오히려 지금 상황과 안 맞는 내용이 나올 수 있는 곳입니다.
- `misc/303`(자동 모험 연대기) — 실제 최근 사건을 요약하는 것 자체가 목적이라 재사용하면 다른 플레이의 기록이 섞여 나옵니다.
- `world/304`(신화 백과사전 용어 추출) — 특정 서술 텍스트에서 언급된 고유명사를 뽑는 기능이라, 다른 텍스트에서 뽑은 결과를 재사용하면 이번 텍스트와 무관한 용어가 나옵니다.
- `misc/302`(꿈/환영), `lore/316`(트라우마), `patches/322`의 NPC 한마디·서사 하이라이트 압축 — 전부 플레이어의 실제 최근 서사/구체적 입력 텍스트를 직접 반영해야 하는 기능입니다.
- `npc/305`(NPC 비밀 아젠다) — 이미 "이 NPC는 한 번만 생성"이라는 자체 가드가 있고, 애초에 그 NPC 고유의 비밀이어야 의미가 있어서 버킷화 자체가 부적절합니다.
- `core/084`의 캐릭터 생성 추천(`_fetchAndCacheSugs`), `job/042`의 수동 직업 탐색(`generateNextJob`) — 둘 다 이미 자체적으로 "충분히 쌓이면 API 호출 생략" 캐시를 갖고 있어서 손댈 필요가 없었습니다.

모두 헤드리스 브라우저로 검증했습니다 — 버킷을 12건 이상 채워둔 상태에서 각 함수를 호출해 `callGeminiDirect`가 전혀 불리지 않은 채로 정확한 재사용 결과(아이템/방/결과/경매/예언)가 반환되는 것, 그리고 통합된 직업 풀에서 실제 팝업 DOM이 재사용된 직업으로 정상 렌더링되는 것까지 확인했습니다.

## 3번(매 턴 서사 자체를 학습) — 사실 이미 만들어져 있었습니다

"고민 많이 해보면서 최적으로" 해달라고 하셔서 매 턴 나오는 선택지/서사 자체를 스킵하는 시스템을 처음부터 설계하려고 코드를 훑던 중, **원본 `taleforge.html`에 이미 정확히 이걸 하는 완성된 시스템이 있는 걸 발견했습니다.** 이전에 말씀하신 "예전에 그렇게 했던 게 있어서"가 바로 이거였습니다 — 새로 만들 필요가 없었고, 대신 이게 실제로 잘 작동하는지 검증하고, 플레이어가 쓸 수 있게 연결하는 쪽으로 방향을 바꿨습니다.

**이미 있던 것 — "로컬 매칭 엔진"(`_meIntercept`, quest/086):**
- 매 턴 AI를 부르기 직전(`callAI` 맨 앞, retryCount===0일 때) 먼저 이 함수를 거칩니다. 과거 기록에서 지금과 "같은 종류의 상황"에 해당하는 응답이 충분히 쌓여 있으면, 그중 하나를 골라 그대로 반환하고 — **API 호출 자체가 발생하지 않습니다.**
- **선택지 클릭만 대상으로 함** — 자유 입력(직접 타이핑)은 절대 캐시하지 않고 항상 AI를 씁니다. 이게 애초에 이 게임이 "선택지 + 아래 채팅창"을 같이 둔 이유 중 하나였다고 하셨던 그 설계입니다.
- 상황 분류가 굉장히 세밀합니다 — 장소·직업·종족·씬 유형(전투/상점/이동/휴식/탐험)·HP 구간·행동 의도·부정 여부·NPC 호감도 구간·골드 구간·시간대·(전투 중이면) 몬스터 이름까지 11개 축을 조합합니다. 예를 들어 "고블린과 전투 중 공격"과 "오크와 전투 중 공격"은 다른 카테고리라 서로 섞이지 않습니다.
- 같은 카테고리에 12건 이상 쌓이면 그 안에서 무작위로 고르되, 최근 기록일수록 조금 더 자주 뽑히는 가중치가 있고(하지만 오래된 것도 계속 등장), 그 12건 안에서도 서로 다른 응답이 30% 이상 다양하지 않으면(같은 문장만 반복될 위험) 아직 AI를 계속 쓰도록 막는 다양성 안전장치까지 있습니다.
- 재사용 시 GS(게임 상태 변화) 중 스탯/골드/아이템처럼 안전한 것만 재실행하고, 퀘스트·플래그처럼 상태 의존적이라 위험한 필드는 건드리지 않습니다.
- `tf-master-playlog`(매 턴 자동 기록, `ai-prompt/148`의 `collectTurnData`)가 이 매칭에 필요한 모든 정보를 이미 정확히 기록하고 있었고, 헤드리스 브라우저로 실제 `callAI()`를 끝까지 실행해 — 과거 기록 15건을 씨딩한 뒤 — API 호출 없이 캐시된 응답이 반환되고 히트 통계(`tf-me-stats`)가 정확히 올라가는 것까지 검증했습니다.

**검증 중 발견한 것 — 완성도는 높은데 플레이어가 도달할 방법이 없었습니다.** 이 매칭 엔진을 켜고 끄는 버튼, 히트율, "하드코딩 룰 추출기"(성숙한 카테고리를 외부에서도 쓸 수 있는 JS 파일로 내보내는 기능 — `previewHardcodeRules`/`exportHardcodeRules`)까지 전부 이미 만들어져 있는데, 이 패널을 여는 버튼이 게임 어디에도 없었습니다(`openP('datacollect')`를 부르는 곳이 코드 전체에 단 한 곳도 없었습니다). 그래서:
- 위 학습 현황 대시보드에 이 매칭 엔진의 히트율을 같이 표시하고, "자세히 보기 · 켜기/끄기 · 룰 추출기" 버튼을 추가해 원래 있던 그 패널(`showCollectionStats()`)을 열 수 있게 연결했습니다. 이제 설정 패널에서 바로 켜고 끌 수 있고, 얼마나 절감되고 있는지 볼 수 있고, 성숙한 카테고리를 룰로 뽑아 하드코딩 준비에 쓸 수도 있습니다.
- 로직 자체는 건드리지 않았습니다 — 이미 잘 설계되어 있었고, 검증 결과로도 그렇습니다.

이게 정말 "최적의 상태"인지에 대한 제 판단: 설계는 이미 신중하게 잘 되어 있어서(다양성 안전장치, 선택지 전용 제한, 안전한 GS만 재실행 등) 처음부터 새로 만드는 것보다 이걸 발견하고 연결하는 게 훨씬 나은 선택이었습니다. 유일하게 남은 손볼 거리가 있다면 "12건 쌓임" 기준 자체를 더 낮추거나 높이는 튜닝 정도인데, 이건 실제로 플레이해보면서 반복감이 느껴지는지 보고 조정하는 게 맞다고 생각합니다 — 지금은 원래 값(12건, 다양성 30%)을 그대로 뒀습니다.

## 게시판(의뢰/정보) 생성도 학습-재사용 적용

`quest/229`의 `generateAIBulletinItems`(마을/도시 게시판에 새 의뢰·정보를 채워 넣는 함수)에도 같은 패턴을 적용했습니다. 장소 유형+트리거 종류+세계관으로 버킷화했고, desc/content가 "상황을 반영"한다고는 하지만 실제로는 장소 타입 수준의 일반적인 내용이라(구체적 사건 텍스트를 직접 인용하지 않음) 재사용에 안전합니다.

참고로 별도의 "NPC 배경스토리 생성기"는 코드베이스에 없었습니다 — NPC는 기본적으로 정적 데이터 풀(`LOC_NPC_POOL`)에서 나오고, AI가 개입하는 두 곳(`generateNpcAgenda`의 비밀/이중성, NPC 대화 중 퀘스트 제안의 인사말·제안 대사)은 지난 응답에서 설명한 이유로 — 각각 "그 NPC 고유의 비밀이어야 의미 있음", "실제 대화 흐름을 그대로 반영해야 함" — 의도적으로 캐싱하지 않았습니다.

## 중세 판타지 외 시나리오 데이터 전부 삭제

이 게임은 실제로는 중세 판타지 하나만 플레이할 수 있습니다 — 캐릭터 생성에서 고를 수 있는 시나리오 목록(`SCENARIOS`)이 원본 `taleforge.html`에서부터 이미 `[MEDIEVAL_SCENARIO]` 하나뿐이었고, 시나리오가 강제로 medieval로 고정되는 코드도 있었습니다. 그런데도 무협·사이버펑크·아포칼립스·신화·스팀펑크용 데이터가 코드 곳곳(28개 파일)에 수천 줄 남아있었습니다 — 전부 `scenarioId==='wuxia'` 같은 조건에 막혀 플레이어가 절대 도달할 수 없는 죽은 데이터였습니다. 이번에 전부 찾아서 지웠습니다.

- **지운 것**: 메인 퀘스트 라인, 장소 데이터베이스, 월드 이벤트, NPC 영웅, 세력(팩션), 아이템 세트, 클리어 보상 아이템/스킬, 히든 퀘스트, 엔딩 조건, 칭호, 전직 스킬, 몬스터/NPC 추가 풀 등 — 전부 medieval이 아닌 시나리오 전용이었던 부분만 골라서 지웠습니다.
- **안 지운 것 (겉보기엔 같은 단어라 헷갈릴 수 있어 정리)**:
  - `religion/120`·`core/122`의 "📖 세계 신화" 패널 — 이건 시나리오가 아니라 이 medieval 세계 자체의 만신전/신화를 보여주는 진짜 게임 기능이라 그대로 뒀습니다.
  - `progression/019`의 `APOCALYPSE_KEY`/`tickApocalypse` — 시나리오와 무관한 "세계 종말 시계" 메커닉의 이름이 우연히 같았을 뿐이라 남겨뒀습니다(해당 함수를 부르던 유일한 호출부는 `apocalypse` 시나리오 전용이어서 그 호출만 지웠습니다).
  - `misc/292`의 "무림 천하대회" 같은 동대륙(east) 이벤트 — 이건 시나리오가 아니라 medieval 세계 안의 "동대륙"이라는 지역이 무협풍 문화를 가진 것으로 설계된 진짜 콘텐츠라 남겨뒀습니다.
  - 장소 이름/텍스트 매칭용 헬퍼(`scenario.includes("무협")` 같은 코드)는 이미 항상 false로 죽어있어서 굳이 손대지 않았습니다 — 지워도 안 지워도 동작은 같고, 잘못 건드리면 오히려 위험한 부분이었습니다.
- **검증**: 매번 파일을 지운 뒤 `node build.js`로 문법 오류를 확인했고, 최종적으로 헤드리스 브라우저로 전체 빌드를 로드해 JS 에러 0건, 장소 98개 정상 로드, medieval 엔딩/팩션 데이터가 정상적으로 조회되는 것까지 확인했습니다. 파일 크기는 9.0MB → 8.7MB로 줄었습니다.
- **되돌리고 싶으시면**: 혹시 나중에 다시 필요해질까 봐, 이 작업 전 상태를 `taleforge-modular-backup-pre-medieval-only` 폴더로 통째로 백업해뒀습니다.

## 장소·몬스터 분포 감사 + 항구/황야 장소 유형 추가

이전에 "장소 유형마다 몬스터가 얼마나 겹치는지, 지역마다 특별한 몬스터가 있는지"를 전체적으로 감사한 결과, 다음을 확인했습니다:

- 기존 9개 장소 유형(special/city/town/village/hamlet/event/dungeon/capital/shrine), 105개 장소가 유형별로 3~6개짜리 아주 얇은 몬스터 풀을 공유하고 있었고, 장소별·대륙별 몬스터 차별화가 전혀 없었습니다(그 어떤 장소 객체도 자기만의 몬스터 목록을 갖고 있지 않았음).
- `dangerLevel`(정밀 레벨대 조정용 필드)은 던전/이벤트/SPECIAL_LOCATIONS 위주 9~41곳에만 있고, 정작 가장 흔한 유형(도시/마을/촌락/수도)은 전무했습니다 — 다만 이건 실제로 문제는 아니었습니다. `getLocationLevelBand()`가 장소 id/이름을 시드로 유형 범위 안에서 결정적으로(항상 같게) 위치를 정하기 때문에, dangerLevel이 없어도 같은 유형 안에서 장소마다 이미 레벨대가 갈립니다.
- `jail`(수감 중 생성되는 장소 유형)에 대응하는 `LOC_MONSTER_POOL` 항목이 아예 없어서, 수감 중 조우가 장소와 전혀 무관한 범용 몬스터 풀로 새고 있었습니다 — 진짜 버그.
- 보스(`BOSS_MONSTERS`)는 18종이 7가지 장소유형 조합으로 꽤 다양했지만, 특정 장소 하나에 묶인 보스는 없었습니다.

이걸 바탕으로 다음을 했습니다:

1. **`jail` 몬스터 풀 버그 수정** — `LOC_MONSTER_POOL`에 `jail` 항목을 추가하고, 매칭되는 유형이 없을 때의 최종 폴백을 범용 `ENCOUNTER_POOL`이 아니라 `city` 풀로 바꿨습니다(향후 새 유형이 추가돼도 완전히 장소 무관한 몬스터가 나오지 않도록).
2. **서사적으로 특별한 장소 21곳에 전용 몬스터 부여** — 왕도, 요정 왕도, 드워프 왕도, 옛 전장, 빙하 던전, 수몰 유적지, 저주받은 폐도, 천계/마계 던전 등 이름 있는 랜드마크급 장소에 그 장소만의 몬스터 2~3종을 추가했습니다(마을·촌락처럼 서로 교체 가능한 평범한 정착지는 일부러 그대로 뒀습니다 — 그런 곳까지 다 차별화하면 오히려 "이 장소는 특별하다"는 신호가 흐려지기 때문입니다). `checkRandomEncounter`가 이 장소별 몬스터를 유형 풀보다 우선해서 섞어 쓰도록 연결했습니다.
3. **새 장소 유형 2개 추가: `port`(항구) / `wilderness`(황야)** — 대륙별로 각 5곳씩(항구: 왕실 조선소항·빙해항·용문항·안개나루·산호만 / 황야: 잊혀진 황무지·서리늑대 벌판·가시덤불 평원·안개 습지·타는 사막), 전용 몬스터·NPC 풀·상점·인터랙션·레벨대(`LOC_TYPE_LEVEL_BAND`)까지 갖춰서 넣었습니다. 새 유형 하나 추가하려면 손대야 할 곳이 코드 전역에 20곳 넘게 흩어져 있어서(상점 허용 목록, 게시판 탭 노출, 세계지도 필터·아이콘·범례, 순찰/체포 판정, 재해 이벤트 타겟, AI 장소 생성 스키마 등) 그 전체를 먼저 훑어 빠짐없이 반영했습니다.
4. **작업 중 발견한 실제 버그 하나 더 수정** — `quest/229`의 `_origRenderBulletinBoard`/`_origDetectAndSetLocation` 캡처가 이전 세션에 고쳤던 `_origGetAllLocations`와 똑같은 종류의 버그였습니다: 진짜 구현이 들어있는 배포 함수(`__tfDeferred_40`/`__tfDeferred_39`)보다 먼저(모듈 최상위, Pass 1에서) 캡처되고 있어서 항상 `undefined`를 잡고 있었습니다 — 즉 AI가 만든 게시판 글 주입과 습격 소문 감지 후킹이 사실상 죽어있었습니다. `_origGetAllLocations` 때와 같은 방식으로, 캡처를 해당 배포 함수(`__tfDeferred_204`) 안으로 옮겨서 고쳤습니다.

**검증**: 매 단계 `node build.js`로 문법 확인 후, 헤드리스 브라우저로 (a) 장소 총 108개(98+10) 정상 로드·유형별 개수 정확, (b) 항구/황야 레벨대 계산 정상, (c) 항구 장소의 NPC 풀이 새로 추가한 항만장/선장/어부로 정상 배정, (d) 실제 장소 패널 렌더 결과에 "항구" 라벨과 "게시판" 탭이 정확히 뜨는 것(= 상점/게시판 허용 목록 수정이 실제로 작동)까지 전부 확인했습니다. JS 에러 0건.

## 자유 텍스트를 안 쓰기로 한 플레이 스타일 — 선택지만으로도 폭넓게

이 게임의 원래 목표는 "스토리·방향은 있지만 자기 멋대로 놀 수 있는 샌드박스"였고, 그걸 위해 자유 텍스트 입력을 만들었습니다. 그런데 API 호출을 최대한 줄이려면(궁극적으로는 완전 하드코딩) 자유 텍스트는 쓸 수 없다는 게 확인됐고, 개발자가 "그럼 선택지만으로도 최대한 폭넓게 놀 수 있게 하자"는 방향을 정했습니다. 조사해보니 선택지 전용 플레이가 실제로 좁아지는 지점이 두 군데 있었습니다:

- AI가 매 턴 만드는 선택지 자체에 "다양한 성격을 섞으라"는 지침이 없어서, 매번 전투/대화류로 수렴하기 쉬웠습니다.
- "로컬 매칭 엔진(Memory-Echo)"이 선택지 클릭만 캐시 대상으로 삼는데(자유 텍스트는 다양성 보호를 위해 애초부터 캐시 제외), 기준이 낮아서(같은 상황 12번↑) 오래 플레이할수록 과거 선택지가 재활용될 확률이 높았습니다.

반영한 것:

1. **선택지 3개 → 4개(+아주 가끔 ⑤ 비밀 선택지)로 확대.** 5개까지 늘리는 것도 검토했지만, 그러면 UI가 복잡해지고 AI가 매번 5개를 의미 있게 다르게 짜내기도 어려워져 오히려 선택지 품질이 떨어질 위험이 있어 4개로 잡았습니다. 선택지 파싱/렌더 파이프라인을 전체 감사해서(`①②③④` 정규식 2군데, 전투 중 선택지 병합 캡, 각종 폴백 배열 등) 빠짐없이 5개까지 안전하게 통과하도록 넓혔습니다. `quest/086-...js`, `misc/076-...js`, `ui/291-...js`.
2. **선택지 생성 지침에 "성격 다양성" 명시.** `CHOICE_DIVERSITY_HINT`라는 공용 문구를 만들어 오프닝/매 턴/`buildLightSystem` 규칙 3곳이 전부 공유하게 했습니다 — "전투/생존형, 대화/설득형, 실리/탐색형, 대담하거나 위험한 선택형 중 최소 2가지 이상 섞을 것" + "NPC 호감도가 충분하면 가끔 관계 진전 방향을, 단서를 좇을 상황이면 가끔 숨겨진 장소/퀘스트로 이어질 선택지를 자연스럽게 섞어도 좋다"는 지침을 추가해, 원래 자유 타이핑으로만 닿던 로맨스·숨겨진 장소·히든 퀘스트 계열도 선택지로 우연히 닿을 여지를 열어줬습니다.
3. **Memory-Echo 재사용 기준 상향.** "API 호출 줄이기"라는 목표와 "매번 새로운 선택지"라는 목표가 정면으로 부딪히는 지점이라, 끄는 대신 재사용이 시작되는 기준을 훨씬 높였습니다 — 최소 표본 5→8, 풀 크기 12→30, 다양성 안전장치 0.3→0.5(풀 30 미만이면 계속 AI 호출 → 60 미만으로 상향). 재사용이 실제로 걸릴 때쯤엔 풀에 변형이 충분히 쌓여 "재사용"이 체감상 "신선함"과 거의 구분이 안 되도록 하는 게 목표입니다. `quest/086-...js` (`ME_MIN_SAMPLES`, `ME_POOL_MIN_SIZE`, `diversityRatio` 체크).
4. **`buildSystem` vs `buildLightSystem` 확인.** 조사 중 `ai-prompt/077`에 있는, 소문·로맨스 서사·왕국 역사까지 담긴 정교한 `buildSystem()`이 실제로는 한 번도 호출되지 않는다는 걸 발견했습니다(모든 실제 호출부가 `window.buildLightSystem||window.buildLightSystem`라는 자기참조 폴백을 쓰고 있었음). 확인해보니 `buildLightSystem`은 파라미터가 더 적은, 이름 그대로 "가벼운" 버전으로 나중에 의도적으로 만들어진 대체품으로 보여서 — 되살리면 프롬프트가 커져 API 비용이 늘어나는 방향이라, 그대로 `buildLightSystem`을 계속 쓰기로 하고 헷갈리는 죽은 자기참조 폴백만 정리했습니다(`core/084-...js`, `quest/086-...js`, 총 6곳).

**검증**: `node build.js`로 문법 확인 후, 샘플 5선택지(①~⑤) 문자열을 실제 파싱 정규식으로 돌려 5개 모두 정확히 분리되는 것, 빌드 결과물에 `ME_MIN_SAMPLES = 8`/`ME_POOL_MIN_SIZE = 30`/`diversityRatio < 0.5`/`pool.length < 60`/전투 선택지 병합 `slice(0,5)`가 전부 반영된 것, 자기참조 폴백이 남아있지 않은 것까지 확인했습니다. JS 에러 0건.

## 선택지 로컬 재조합 생성기 — Memory-Echo의 근본적 한계 보완

위 3번(Memory-Echo 재사용 기준 상향)을 반영한 뒤, "같은 상황이 정말 30번씩 벌어지는 게 현실적이냐"는 질문이 나왔습니다. 실제로 계산해보니 아닙니다 — 카테고리 축이 11개(장소·직업·종족·씬타입·HP대역 5·호감도 5·골드대역 4·시간대 4·의도 12종 등)라 조합 폭이 수십만~수백만이고, 그중 정확히 같은 조합이 30번 반복되는 건 "매번 돌아가는 익숙한 거점(고향 마을 등)" 몇 곳 말고는 사실상 일어나지 않습니다. 즉 Memory-Echo 자체는 "실제로 AI가 만들어낸 문장을 재생하는 캐시"라 다양성의 천장이 과거 AI 호출 횟수에 묶여있고, 반복 방문이 부족한 대부분의 상황에서는 재사용이 걸릴 일 자체가 드뭅니다.

그래서 완전히 다른 종류의 해법을 하나 더 추가했습니다 — 다른 로그라이크 게임들이 쓰는 "단어 몇 개를 재조합해 수만 가지 문장을 낸다"는 방식입니다. Memory-Echo와 달리 이건 **AI 호출도, 같은 상황의 반복 방문도 전혀 필요 없습니다.** 사람이 미리 준비해둔 문장 틀(카테고리별 10개씩, 총 40개) × 그 순간 실제 게임 상태(현재 NPC 이름·몬스터 이름·장소 이름)를 즉석에서 조합해 매 턴 최소 1개의 선택지를 새로 만들어냅니다.

- `quest/086-...js`에 `generateLocalFlavorChoices(count)` 추가 — 대화/설득형·실리/탐색형·대담/위험형·전투/경계형 4개 카테고리, 카테고리당 문장 틀 10개. `{t}` 자리에 그 장면의 실제 NPC/몬스터/장소 이름을 채워 넣습니다(없으면 카테고리에 맞는 일반 명사로 대체).
- **한글 조사 처리**: "사람과"/"그림자와", "도적을"/"엘프를", "마을로"/"사람으로"처럼 채워 넣는 단어의 받침 유무에 따라 조사가 달라지는데, 문장 틀에 조사를 그냥 박아두면 절반은 문법이 깨집니다. `_josa(word, type)` 함수가 마지막 글자의 유니코드로 받침 유무(및 ㄹ받침 예외 — "마을로부터"이지 "마을으로부터"가 아님)를 계산해서 항상 맞는 조사를 붙입니다.
- `ui/291-...js`의 선택지 렌더 훅에 연결 — AI(또는 Memory-Echo 캐시)가 준 선택지를 절대 밀어내지 않고, 자리가 남을 때만(최대 5개까지) 뒤에 이어붙입니다. 턴이 바뀔 때만 새로 채우고, 같은 턴 안에서 여러 번 렌더링돼도 중복 주입하지 않습니다. 이 덕분에 Memory-Echo가 예전 선택지를 그대로 재생한 턴에도 최소 하나는 항상 그 자리에서 새로 만든, 한 번도 안 나온 선택지가 섞입니다.

**검증**: 실제 게임 로직으로 단어(사람/그림자/도적/호랑이/엘프/토끼/늑대/마법사/마을 등, 받침 있음·없음·ㄹ받침 전부 포함)를 채워 60~80회씩 생성해 조사가 전부 올바르게 붙는 것을 확인했고, `S.choices`에 AI 선택지 4개를 넣고 렌더 훅을 실제로 호출해 (a) 로컬 선택지 1개가 자연스럽게 추가되어 5개가 되는 것, (b) 같은 턴 재렌더링 시 중복 주입 안 되는 것, (c) 턴이 바뀌면 새 로컬 선택지로 갱신되는 것까지 전부 확인했습니다. JS 에러 0건.

## 숨겨진 장소 로컬 발견 규칙 — 히든 장소가 AI 없이도 열리도록

"히든 퀘스트나 숨겨진 장소도 AI 없이 잘 작동하는지" 확인해달라는 요청에 조사해보니, 안 좋은 소식이었습니다 — **둘 다 지금 구조로는 AI 없이는 절대 발동하지 않습니다.** 두 시스템 모두 AI의 `<gs>{...}</gs>` 응답에서 특정 필드(장소는 `hidden_location_found`, 퀘스트는 `hidden_quest_done`)를 파싱해야만 처리되고, 그 필드를 다른 방식(전투 결과·평판·행동 이력 등)으로 로컬에서 설정하는 코드는 어디에도 없었습니다. Memory-Echo 캐시 히트 턴도 확인했는데(`sendMsg`의 `<gs>` 파싱, 실시간 응답인지 캐시 재생인지 구분하는 분기가 전혀 없음), 캐시가 그 턴을 대신 처리하면 "지금 조건이 충족됐는지" 새로 판단하는 일 자체가 일어나지 않습니다.

두 시스템의 난이도는 달랐습니다:
- **숨겨진 장소**(오크 은신처·위장 저택가·균열의 안식처·죽음의 계곡)는 발견 조건이 "우호적 접촉", "밤에 방문", "단서 추적" 같은, 이미 게임이 추적 중인 값(대륙·시간대)에 가까워서 로컬 규칙으로 바꿀 수 있었습니다.
- **히든 퀘스트**(75개)는 처음엔 손대지 않을 생각이었습니다 — 각각 "NPC가 트라우마를 고백 → 플레이어와 상징적 사건을 겪음 → 감정적으로 매듭"짓는 여러 단계짜리 서사라, 로컬 규칙으로 흉내 내려면 그 서사를 통째로 대체해야 한다고 봤기 때문입니다. 그런데 이후 개발자 요청으로 다시 파보니 예상과 달랐습니다 — 아래 별도 섹션 참고.

그 외 히든 퀘스트로 잠긴 3곳(태초의 화로·전설의 사냥터·감시자의 영역, `hiddenUntilDiscovered:true`지만 `discoveryHint`가 아니라 퀘스트 완료로만 열림)은 별도 규칙을 새로 만들지 않았습니다 — 대신 아래 히든 퀘스트 로컬화 작업이 그 세 곳을 잠그고 있는 히든 퀘스트 자체를 로컬로 완료시키므로, 완료 시 원래 있던 "영구 발견 등록" 로직이 그대로 실행되어 자연히 함께 열립니다. 특히 「감시자의 영역」을 잠그고 있는 「금서의 무게」는 학자 전용 퀘스트라 코드에 있는 우회 발견 차단 안전장치와도 충돌하지 않습니다(그 안전장치는 `hidden_location_found` 범용 필드로 직접 발견되는 것만 막지, 정상적으로 퀘스트를 완료해서 여는 경로는 원래도 허용되어 있었습니다).

반영한 것 — `quest/086-...js`에 `checkHiddenLocationDiscoveryLocal()` 추가:

- 매 턴(`sendMsg`의 `<gs>` 처리 직후, 선택지든 타이핑이든·실시간 AI든 Memory-Echo 캐시든 전부) 호출되어, 현재 위치의 대륙과 시간대, 그리고 대륙별 누적 체류 턴수(`tf-continent-visit-count`, 새 로컬 키)만으로 4곳을 각각 체크합니다.
  - 은둔부족 거점 그롬바르: 북부 대륙 누적 3턴↑
  - 위장 저택가: 중앙 대륙에서 밤을 맞이함(즉시)
  - 균열의 안식처: 동남 대륙 누적 3턴↑
  - 죽음의 계곡: 북부 대륙에서 밤을 맞이함(즉시 — 오크 거점과 같은 대륙이지만 밤 조건으로 구분)
- 발견 시 기존 AI 경로와 **완전히 같은 저장소**(`tf-discovered-hidden-locs`)에 기록하고 같은 토스트를 띄웁니다 — 그래서 AI 서사 경로를 없앤 게 아니라 나란히 추가한 것입니다. 둘 중 뭐가 먼저 발견시키든(로컬이 먼저든, AI가 여전히 살아있어 서사로 먼저 발견시키든) 같은 id를 공유하니 중복 없이 자연스럽게 합쳐집니다.

**검증**: 새 브라우저 페이지마다 조건을 다르게 세팅해 6가지 시나리오를 실제로 돌렸습니다 — 북부 3턴 방문 시 오크 거점 발견, 중앙+밤에 위장 저택가 즉시 발견, 북부+밤에 죽음의 계곡 발견, 동남 3턴 방문 시 균열의 안식처 발견, 중앙+낮 3턴은 아무것도 안 열리는 것(오탐 없음), 북부 2턴(임계값 미달)은 아직 안 열리는 것까지 전부 의도대로 동작했습니다. 마지막으로 `getAllLocations()`로 전/후 비교까지 확인해 — 발견 전엔 지도에 없다가, 로컬 규칙 발동 후엔 실제로 "은둔부족 거점 그롬바르"라는 이름으로 지도에 나타나는 전체 흐름을 검증했습니다. JS 에러 0건.

## 히든 퀘스트 75개 전부 AI 없이 완료 가능하게 — 사실 이미 설계는 그래 있었다

바로 위 섹션에서 "히든 퀘스트는 각각 즉흥 서사라 로컬 대체가 불가능하다"고 적었는데, 개발자가 "AI가 퀘스트를 만들 수는 있지만, 작동시키는 조건 자체는 로컬로 바꿀 수 없냐"고 다시 요청해서 코드를 더 깊이 파봤더니 — **완전히 잘못 짚었던 걸 발견했습니다.** 히든 퀘스트 75개 전부 데이터 자체에 이미 완벽하게 로컬화된 발동 조건이 구조화된 필드로 들어있었습니다:

```js
{ id:"hq_gladiator_names_in_sand", ...
  condition:"gladiator_master",
  conditionDesc:"현재 직업 투기사 + 근력 70 이상 + 맨손 전투 5회 이상", ... }
```

그리고 이 `condition` 필드를 실제로 검사하는 함수(`checkHiddenQuestCondition`, `quest/041-...js`)도 이미 완성돼 있었습니다 — 직업 숙련도, 제작소 등급, 각종 활동 로그 횟수, 업보, 세력 게이지 등 전부 로컬에서 이미 추적 중인 값만 씁니다. 75개 퀘스트가 쓰는 조건 73종을 전수 대조해봤는데 **빠짐없이 100% 커버**돼 있었습니다. 심지어 "조건 충족 시 자동으로 퀘스트를 활성화한다"(`availableHiddenQuests.forEach(q => activateHiddenQuest(q.id))`)는 코드까지 이미 작성돼 있었어요 — 다만 그 코드가 들어있던 곳이 앞서 발견한, **한 번도 호출되지 않는 죽은 `buildSystem` 프롬프트 파일(`ai-prompt/077`) 안**이었습니다. 즉 설계는 이미 AI 없이 돌아가도록 완성돼 있었는데, 그 배선이 죽은 파일에 갇혀서 실제 게임에는 한 번도 연결된 적이 없었던 것입니다.

반영한 것 — `quest/041-...js`에 `checkHiddenQuestsLocal()` 추가, 살아있는 경로(`quest/086`의 `sendMsg`, 위 숨겨진 장소 체크 바로 다음)에 연결:

- 매 턴 현재 직업 숙련도·제작소 상태·업보·세력 평판·게임 시간대 등 로컬 상태로 `gameData`를 조립해 `getAvailableHiddenQuests()`를 호출합니다.
- 조건을 충족한(아직 활성화·완료되지 않은) 퀘스트가 있으면 즉시 `activateHiddenQuest` + `completeHiddenQuest`를 연달아 호출해 보상을 지급합니다. 별도의 "진행 중" 단계를 로컬에서 표현할 신호가 없어서 조건 충족 = 완료로 취급했습니다 — 애초에 조건 자체가("대장간 레벨3 + 채광 10회" 같은) 이미 상당한 성취라, 그 자체를 서사적 완결점으로 봐도 무리가 없습니다.
- `completeHiddenQuest`에는 이미 퀘스트별 보상 지급 로직(칭호·설계도·영구 장소 해금 등)이 들어있어서 그대로 재사용됩니다 — 예를 들어 대장장이 히든 퀘스트(「태초의 화로」)를 로컬로 완료시키면, 그 안에 있던 "태초 설계도 3종 지급 + 「태초의 화로」 장소를 지도에 영구 등록" 로직이 원래 그대로 실행됩니다. 즉 히든 퀘스트로만 열리던 3개 장소(태초의 화로·전설의 사냥터·감시자의 영역)도 이 작업으로 자연스럽게 AI 없이 열리게 됐습니다.
- AI가 여전히 살아있어 서사로 먼저 완료시킨다면 그것도 그대로 작동합니다 — 이미 완료된 id는 로컬 체크에서 자연히 건너뜁니다.

**검증**: (a) 단순 조건(`night` — 밤 시간대) 퀘스트가 조건 충족 즉시 완료 처리되는 것, 낮에는 완료 안 되는 것, (b) 같은 함수를 3번 연속 호출해도 완료 시각이 안 바뀌는 것(중복 지급 방지), (c) 복합 조건(대장간 레벨3+채광로그10회 — 「태초의 화로」) 퀘스트가 실제로 완료되고 **보상 로직의 연쇄 효과(태초의 화로 장소가 `tf-permanent-unlocked-locs`에 영구 등록)까지 실제로 발동**하는 것, (d) 완전히 빈 캐릭터 상태로 10턴을 연속 호출해도 아무 것도 잘못 완료되지 않고 에러도 없는 것까지 전부 실제 게임 로직으로 확인했습니다. JS 에러 0건.

## 실제로 브라우저를 켜서 확인 — 그 과정에서 발견한 진짜 버그 2개

지금까지의 검증은 전부 개별 함수를 직접 호출해서 결과를 확인하는 방식이었습니다. "직접 켜서 확인해볼 수 있냐"는 요청을 받고, 이번엔 진짜로 헤드리스 브라우저에 API 키·캐릭터·세션을 실제 저장 형식대로 심어서 **진짜 시작 화면 → 이어하기 모달 → 채팅 화면 → 세계지도 → 장소 패널까지 실제 버튼을 클릭하며** 확인했습니다. 이 과정에서 지금까지의 함수 단위 테스트로는 못 잡았던, 게임을 실제로 켜야만 드러나는 버그를 2개 발견해서 같이 고쳤습니다(둘 다 이번 세션의 다른 작업과는 무관한, 원래부터 있던 버그입니다):

1. **`window.updateHeader` — 거의 모든 행동에서 죽는 버그.** `misc/230-...js`에 헤더 갱신 함수를 감싸는 코드가 두 겹 있는데, 첫 번째 겹(둠 클록 배지 추가용)은 정상이었지만 바로 다음 두 번째 겹(방랑자 축 막대 추가용)이 `_origUpdateHeader`라는, **모듈 최상위(Pass 1)에서 캡처된 변수**를 참조하고 있었습니다 — 이 세션에서 여러 번 고쳤던 것과 완전히 같은 버그 패턴입니다(진짜 구현은 Pass 2에서만 설정되므로 Pass 1 캡처는 항상 undefined). 이 값으로 `.apply()`를 호출하니, 헤더가 갱신되는 거의 모든 곳(골드 변화·퀘스트 완료·스탯 변화·세션 이어하기 등 사실상 대부분의 행동)에서 예외가 터졌습니다. 배포 함수 안에서 새로 캡처하도록 고쳤습니다.
2. **세계지도 화면이 아예 안 열리는 버그.** `getWeatherForecast()`(`quest/086`)는 `'clear'`/`'rain'` 같은 원시 문자열 배열을 반환하는데, 세계지도를 그리는 `buildOverworldMapHTML()`(`quest/229`)은 이걸 `{icon, weather, eff}` 형태의 객체로 착각하고 `weather.eff.split('—')`를 호출하고 있었습니다 — 날씨 시스템과 지도 시스템이 서로 다른 형식을 기대한 채 한 번도 실제로 맞춰본 적이 없었던 것으로 보입니다. 지도를 열 때마다(즉 거의 모든 플레이에서) 예외가 나서 지도 패널 자체가 안 열리고 있었습니다. 실제 날씨 데이터(`WEATHER_EFFECTS`)에서 아이콘·이름을 올바르게 조회하도록 고쳤습니다.

**검증**: 실제 API 키·캐릭터·세션을 `localStorage`에 실제 저장 형식대로 심고 페이지를 새로고침 → "시작하기" 클릭 → 이어하기 모달에서 실제로 제 캐릭터("테스트용사 · 인간 항해사 · 3턴")가 뜨는 것 확인 → "이어서 진행" 클릭까지 실제 버튼 클릭으로 진행했습니다. 채팅 화면에서 AI가 준 선택지 3개 뒤에 로컬 재조합 선택지 2개("숨을 고르며 다음 상황에 대비한다" 등)가 자연스럽게 붙어 총 5개로 뜨는 것도 실제 화면에서 확인했습니다. 위 두 버그를 고친 뒤에는 세계지도가 정상적으로 열려 51개 마을·도시(port 포함)가 올바르게 분류되어 나열됐고, 장소 패널에서는 실제로 작성한 빙해항의 설명("일 년 중 절반이 얼어붙는...")과 상점 아이템("방한 외투", "고래기름")까지 화면에 정확히 렌더링되는 것을 스크린샷으로 확인했습니다. JS 에러 0건.

src/

  race/       종족 (엘프·드워프·뱀파이어 등)

  religion/   종교
  summon/     소환수·권속·혈통
  progression/ 회차·환생·업적·칭호

각 파일 이름은 `번호-원래섹션제목.js` 형태입니다. 번호는 원본 파일에서의 순서를 그대로 유지한 것입니다.

`data/010-스킬-강화-시스템.js`에 있습니다 (해당 섹션에 뺄 만한 순수 데이터가 없으면 데이터 파일 자체가
없습니다).
