# 도트 아이콘 생성기(pixelart-gen) 작업 메모장

> 이 메모장은 이 `pixelart-gen/` 폴더 **안에** 산다. 이 폴더를 통째로
> 다른 프로젝트에 복사해가도 이 메모장이 같이 따라가도록 하기 위해서다
> (TaleForge 프로젝트 전체의 진행 상황은 프로젝트 루트의
> `작업메모장.md`에 따로 기록 — 거긴 이 툴 얘기를 요약만 하고, 상세
> 이력은 여기 남긴다).

최종 갱신: 2026-09-15

---

## 1. 이 툴이 뭔가

게임에 넣을 도트(픽셀 아트) 이미지를 **외부 AI 이미지 생성 API 없이,
순수 코드만으로** 자동 생성하는 툴. 이름(id)을 시드로 결정론적으로
그림을 계산해서 그린다 — 같은 이름은 언제 다시 돌려도 항상 같은
그림이 나온다.

**왜 이 방식을 골랐나** (사용자와의 대화에서 나온 이유):
- 외부 AI 이미지 생성 API는 실제로는 "도트" 그림을 안정적으로 뽑아주지
  않는다(요청하신 스타일이 아님) + 항목 수가 4,400개 정도로 많아서
  API 호출 비용/네트워크 의존성이 부담스러움.
- 용량 문제 — 도트 특성상 인덱스 컬러 PNG로 압축하면 장당 평균
  200바이트대로 극히 작음(직접 측정 확인).
- "요즘 게임처럼" 이미지 파일을 따로 분리해서 쓰는 구조를 원함
  (HTML에 base64로 안 박아넣음) — 나중에 앱으로 만들어 판매할
  계획이라 이 구조가 맞다고 판단.

## 2. 구조 (파일별 역할)

```
tools/pixelart-gen/
  png-encoder.js   범용 PNG 인코더. node 내장 zlib만 사용, 외부 의존성 0.
                   인덱스 컬러(팔레트) + tRNS(투명) 지원.
  generators.js    핵심 생성 로직. generateIcon({id, name, category, rarity, type}) 하나로
                   16x16 논리 그리드를 계산해서 PNG용 픽셀 버퍼를 만든다.
  load-data-module.js  범용에 가까움(TaleForge 전용은 아니지만 특정
                   빌드 관례에 의존). esbuild로 ES 모듈을 CJS로 변환해서
                   실제 실행 — src/data/*.js를 정규식이 아니라 진짜 JS
                   객체로 읽어들인다. import가 있는 파일은 만능 스텁으로
                   무해하게 흘려보냄.
  scan-entities.js TaleForge의 src/data/*.js를 훑어서 그림이 필요한
                   항목(아이템/몬스터/NPC/장소/스킬/칭호/업적 등) 목록을
                   뽑아내는 스캐너. *이 파일만 TaleForge 전용* — 다른
                   게임에 옮기면 그 게임 데이터 구조에 맞게 새로 짜야 함.
                   실행: `node scan-entities.js` → scan-result.json 생성.
  generate.js      (예정) scan-entities.js 결과 + generators.js를 엮어서
                   실제 assets/img/*.png 전부와 manifest.json을 만드는
                   메인 CLI.
  메모장.md         이 파일.
```

## 3. 재사용성 — 다른 게임에도 쓸 수 있나?

**`png-encoder.js` + `generators.js`는 완전 범용** — TaleForge를 아는
코드가 한 줄도 없다. 다른 게임에서도 그대로 복사해서
`generateIcon({id, name, category, rarity, type})`만 호출하면 동작한다.

게임마다 다시 만져야 하는 부분:
1. **카테고리 모양 틀(SHAPES)** — 지금은 중세 판타지 RPG에 맞춘
   무기/방패/물약/장신구/재료/몬스터/NPC/장소(지형) 8종뿐이다. 다른
   장르(SF, 현대물 등)면 그 장르에 맞는 모양 틀을 `SHAPES`/
   `TERRAIN_SHAPES` 객체에 새로 추가하면 된다 — 기존 구조를 안
   바꾸고 새 카테고리 키만 더하면 됨.
2. **`scan-entities.js`** — 어느 게임이든 "데이터에서 그림이 필요한
   항목을 어떻게 찾아낼지"는 그 게임의 데이터 구조에 달려있으므로
   매번 새로 짜야 하는 유일한 부분.

### 설계 결정: 매니페스트를 JSON이 아니라 JS로도 내보내는 이유

`dist/taleforge.html`은 단일 파일로 배포되고 보통 `file://`로 직접
열린다. 그 상태에서 `fetch('assets/manifest.json')`을 쓰면 브라우저의
로컬 파일 CORS 정책에 걸려 실패할 수 있다(환경마다 다르게 동작해서
신뢰할 수 없음). 그래서 매니페스트 자체는 **JS 데이터 모듈로 번들
안에 직접 포함**시키고(`900-pixelart-manifest.js`, `window.PIXEL_ART_MANIFEST`),
실제 이미지 파일만 `<img src="assets/...">`로 참조한다 — `<img src>`는
`fetch()`와 달리 file:// 에서도 CORS 문제 없이 잘 로드된다.

## 7. 2차 라운드 — "하나씩 다 해서 완성" (전수 자동 연결)

사용자가 "대표적인 곳만 말고 하나씩 다 해서 완성하자"고 요청해서,
남은 약 1,570곳의 `.icon` 참조를 전수 조사해 안전하게 자동 연결하는
작업을 진행했다.

### 7-1. 새로 발견한 카테고리: badge (등급/단계/티어)

`name`+`icon` 쌍만 찾던 스캐너가 놓치고 있던 큰 부류를 발견했다 —
`DUNGEON_GRADES` 같은 "등급/단계" 데이터는 `name` 대신 `label` 필드를
쓴다(실측: 30개+ 파일). 스캐너를 확장해서 `label`도 이름 후보로
인식하게 하고, 새 카테고리 `badge`(메달 모양, achievement와 시각
언어 공유)를 추가했다. 그 결과:

- 전체 스캔 항목: 2,859개 → **3,499개**로 증가(badge 604개 신규)
- **버그 발견·수정**: 처음엔 badge 판정이 너무 넓어서 EMOTION_DEFS 같은
  "진짜 표정 이모지"(😊😠😢...)까지 추상 메달로 바꿔버릴 뻔했다 —
  감정 이모지는 그 자체로 의미를 전달하는 그림이라 메달로 바꾸면
  오히려 정보 손실이다. `EMOTION|MOOD` 키워드가 들어간 테이블은
  badge 기본 분류에서 제외하도록 고쳤다.
- **버그 발견·수정 (더 심각함)**: `getEntityIconHTML()`이 `entity.id`/
  `entity.name`만 보고 있어서, label 필드를 쓰는 badge류 604개
  전부가 실제 게임에서는 이미지를 절대 못 찾고 있었다(매니페스트엔
  제대로 들어있는데 조회 키가 틀렸던 것). `entity.label`도 이름
  후보로 보도록 헬퍼를 고쳐서 실제로 연결되는 것까지 확인했다.

### 7-2. 자동 와이어링 툴 2개 신규 제작

`tools/pixelart-gen/wire-icons.js`와 `wire-icons2.js` — 코드베이스
전체를 훑어서 안전한 패턴만 골라 자동으로
`getEntityIconHTML(...)` 호출로 감싸는 스크립트. 둘 다 드라이런으로
먼저 검토하고 적용했다.

- **wire-icons.js**: "태그 안에 아이콘 표현식 하나만 있는" 가장 좁고
  안전한 패턴(`<span>${x.icon}</span>` 형태)만 매치. 213곳 자동 연결.
- **wire-icons2.js**: 태그 안에 다른 텍스트(`${x.icon} ${x.name}`
  같은 혼합 콘텐츠)가 섞여 있어도, `${...}` 보간식 하나만 콕 집어서
  안전하게 치환하도록 확장. 처음엔 571곳이 매치됐는데, **그중 상당수가
  실제로는 위험한 오탐이었다**:
  - `ai-prompt/077`(AI 시스템 프롬프트 조립 파일) 155곳 — 전부 AI에게
    보내는 지시문 텍스트(`"...서사에 자연스럽게 반영하십시오"`)였다.
    여기에 `<img>` HTML을 끼워 넣었으면 AI 프롬프트 자체가 깨졌을
    것이다.
  - `npc/067`(NPC 관계망) 57곳 — `events.push({msg: ...})` 형태의
    월드 뉴스/소문 텍스트였다. 이것도 HTML을 끼워 넣으면 안 되는
    순수 서술문.
  - **안전장치 추가**: 그 줄에 리터럴 `<span` 또는 `<div` 태그가
    실제로 있는지 확인하는 필터를 추가했다 — 진짜 HTML을 만드는
    코드는 항상 태그가 있고, 프롬프트/서술 텍스트는 태그가 전혀
    없다는 걸 실측으로 확인하고 활용한 것. 이 필터 하나로 571 → 133
    으로 줄었고, 위 두 위험 사례가 전부 자동으로 빠졌다. 133곳

## 9. 3차 라운드 — 토스트 알림 + NPC 소문/월드뉴스도 이미지화

사용자가 "나머지 이모지 부분(토스트, 소문/뉴스)도 이미지로 바꿔줄
수 있어?"라고 요청해서 진행. 두 영역 모두 겉보기엔 비슷해 보여도
실제로는 완전히 다른 제약이 있었다 — 아래에 그 판단 과정을 남긴다.

### 9-1. 토스트 알림 (329건 중 89건 자동 연결)

`toast()`가 지금까지 `t.textContent = msg`로 순수 텍스트만 넣고
있었다 — 이미지 태그를 넣어도 글자 그대로만 보이는 구조였다.
`toast(msg, ms, icon)`처럼 **3번째 인자**를 새로 받도록 고쳐서,
아이콘은 신뢰 가능한(코드가 직접 만든) HTML만 별도 DOM 요소로
안전하게 붙이고, `msg` 자체는 여전히 textContent로 그대로 둔다
(AI가 파싱한 자유 텍스트가 섞여도 안전).

`wire-toast-icons.js` 신규 제작 — `toast(\`${x.icon} 나머지텍스트\`, ms)`
처럼 아이콘이 템플릿 맨 앞에 단독으로 오는 패턴만 찾아서
`toast(\`나머지텍스트\`, ms, x)`로 기계적으로 바꿔친다. 94곳 매치,
89곳 자동 적용(40개 파일). 중간에 아이콘이 끼는 복잡한 경우는
손대지 않고 기존 이모지 그대로 둠.

### 9-2. NPC 소문/월드뉴스 (renderFactionNewsBulletin) — 왜 "정확한
엔티티별 이미지"가 아니라 "이벤트 종류별 대표 아이콘"인가

처음엔 토스트와 똑같이 접근하려 했는데, 조사해보니 두 가지 진짜
장벽이 있었다:

1. **msg 문자열이 AI 프롬프트에도 그대로 재사용된다** —
   `misc/076`의 세계 전황 힌트 빌더가 `tf-faction-news-queue`의
   `n.msg`를 그대로 가져다 AI 프롬프트에 박아넣는다
   (`const recent = q.slice(0,2).map(n=>n.msg).join(' / ')`). 여기에
   HTML을 넣으면 AI 프롬프트 자체가 깨진다 — 이건 UI 문제가 아니라
   AI 프롬프트 오염 문제.
2. **NPC/세력 둘 다 "특정 엔티티" 정밀 이미지가 애초에 불가능**:
   - NPC(로맨스·결혼·불화·사망 소문의 당사자)는 플레이 중 동적으로
     생성되는 캐릭터라, 애초에 정적 데이터 스캔 대상(`src/data/`)에
     존재한 적이 없다 — 무슨 수를 써도 절대 실제 이미지를 못 찾고
     항상 이모지로 폴백한다.
   - 세력(`FACTIONS_BY_SCENARIO`)은 `src/data/`가 아니라
     `npc/067-③-NPC-관계망-시스템.js` 로직 파일 안에 직접 정의돼
     있어서 스캐너가 애초에 본 적이 없다. 게다가 `name` 필드도 없이
     객체 키로만 존재해서, 제대로 하려면 이 프로젝트의 기존
     data/logic 분리 관례를 따라 `src/data/`로 빼내는 리팩터링이
     필요하다 — 이번 도트 아이콘 작업 범위를 넘어서는 더 큰 작업.

사용자가 "AI는 어차피 나중에 다 뺄 거잖아"라고 물어봤지만, "나중에"가
언제일지 모르는 채로 지금 당장 AI 프롬프트를 오염시키는 리스크를
감수할 필요는 없었다 — **msg 원문은 전혀 안 건드리고, "화면에 보여줄
때만" 안전하게 치환하는 방법**을 찾아서 그 트레이드오프 자체를
없앴다:

- `tools/pixelart-gen/event-icons.js`: 이 뉴스 시스템에서 반복
  등장하는 "사건 종류" 이모지 14개(💕💍💢💀⚡🌿💌🔥🕊️🤝⚔️💥📜📰)만
  정의. `generate.js`가 이 목록을 읽어서 `badge` 카테고리로 이미지를
  만들고 `manifest.byName[그 이모지 문자]`에 직접 등록한다(항상
  `generate.js` 안에서 같이 돌아가므로 나중에 다시 생성해도 절대
  누락되지 않음).
- `utils.js`에 `decorateEmojiIcons(escapedHtml)` 신규 추가 — **이미
  `esc()`로 이스케이프된 뒤의** HTML 문자열만 받아서, 그 안의 알려진
  이모지 문자만 신뢰 가능한 배지 이미지로 치환한다. `esc()` 이후
  단계라 원본 텍스트에 `<`/`>`가 있었어도 이미 무력화된 뒤라 안전.
- `npc/067`의 `renderFactionNewsBulletin()` 표시 지점 2곳만 수정
  (`esc(n.msg)` → `decorateEmojiIcons(esc(n.msg))`, 타입 아이콘 단독
  span도 함께 연결). **메시지를 만드는 코드(`events.push({msg:...})`,
  `BIG_EVENTS` 등)는 단 한 글자도 안 건드림** — AI 프롬프트로 가는
  경로와 완전히 분리됨.
- Playwright로 검증: 가짜 뉴스 큐를 심고 `renderFactionNewsBulletin()`
  호출 → 실제 이미지 5개 렌더 확인 + `n.msg` 원본 문자열이 전혀
  변형되지 않았음을 직접 대조 확인.

### 11-2. badge(618개) 모양 다양성 추가

- **핵심 설계**: 개별 항목(id)이 아니라 **같은 배열/그룹

  "등급 1~5"는 항상 같은 모양에 색만 달라지고, 아예 다른 배열
  (`FAITH_TIERS` 등)은 다른 모양을 쓰게 했다 — 개별 시드로 하면
  같은 등급 테이블 안에서도 모양이 뒤죽박죽 섞여서 오히려 부자연스러움.
- 366개 서로 다른 그룹에 대해 5종 모양이 61~82개씩 고르게 분산되는

- Playwright로 5종 모양이 실제로 시각적으로 뚜렷이 다르게 렌더되는

  더 맞음.
- 그래도 남는 `unclassified`(210개, 143개 서로 다른 그룹)도 badge와
  같은 방식으로 **`UNCLASSIFIED_VARIANTS`(재료 덩어리/빛나는 구슬/
  매달린 태그 3종)를 그룹 단위로 분산**해서 전부 똑같은 돌덩이만
  나오는 문제를 완화.
- 개별 항목의 이모지가 더 구체적인 신호(예: 💀 해골 아이콘이 붙은
  섬 하나는 monster로 분류됨)면 그쪽이 우선한다 — 기존 설계 그대로,
  버그 아님(직접 실측으로 확인).

### 11-4. 하드코딩 이모지 리터럴(694건) — "연결할 엔티티가 없는 경우"도 해결

9-3에서 "이 도구의 대상 범위 밖"이라고 적어뒀던 항목인데, "다
진행해" 지시로 다시 검토해서 방법을 찾았다. `toast('📋 ...', 2000)`
처럼 `.icon` 필드 참조가 아니라 메시지 문자열 맨 앞에 그냥 이모지가
박혀 있는 경우 — 694건, 실제로는 **154종의 서로 다른 이모지가
반복 사용**되고 있었다(⚠️ 58회, ✨ 35회, 💀 28회...).

- 호출부 694곳을 일일이 고치는 대신, **`toast()` 자체가 런타임에
  메시지 맨 앞 글자를 자동 인식**하도록 바꿨다 — 매니페스트에
  등록된 이모지면 떼어내서 이미지로, 나머지 문자열은 여전히
  `textContent`(그대로 안전). 등록 안 된 이모지는 그냥 원래처럼
  텍스트 그대로 남는다(폴백 없이 자연스럽게 무시).
- `tools/pixelart-gen/common-icons.js` 신규 — 9-2의 event-icons.js
  (14개, 사건 종류)와 같은 방식으로 **범용 알림 이모지 143개**를
  등록(9-2의 14개와 겹치는 건 자동 중복 제거). `generate.js`에
  `registerEmojiIcon()` 공용 헬퍼로 리팩터링해서 두 목록을 같은
  코드로 처리.
- `decorateEmojiIcons()`도 하드코딩 정규식 목록 대신, **매니페스트에
  등록된 "순수 이모지" 키를 매번 동적으로 읽어서** 정규식을 만들도록
  일반화 — 앞으로 event-icons.js/common-icons.js에 뭘 추가해도 이
  함수를 따로 안 고쳐도 됨. `toastHTML()`도 내부적으로
  `decorateEmojiIcons()`를 한 번 더 거치도록 연결해서 문장 맨 앞
  하드코딩 이모지(예: "🎁 ...")까지 커버.
- Playwright로 4가지 케이스 전부 검증: (1) 실제 하드코딩 이모지
  toast → 이미지 변환 확인, (2) 매니페스트에 없는 임의 이모지 → 원본
  그대로 안전하게 유지, (3) 인식된 이모지 뒤에 `<b>악성</b>` 같은
  HTML 흉내 텍스트가 와도 `esc()` 없이도 여전히 textContent라서
  안전(XSS 방어 확인), (4) toastHTML 쪽 리터럴 이모지도 변환 확인.

## 12. 5차 라운드 — svgIcon(손그린 SVG 아이콘) 시스템 전체 도트화

"아이콘부터 배경까지 다 도트로 넣는다고 했는데, 아이콘/배경만 하는
거 아니지?"라는 사용자 질문에 조사해보니, 실제로 이 게임에는 우리
엔티티 아이콘 파이프라인과 완전히 별개인 **손으로 그린 SVG
라인아트 시스템**이 있었다(등급/단계/랭크 표시용, 환생·언데드·
수인족·공허·인간각성·소환·만신전·직업·세트아이템·NPC관계망 등
10개+ 시스템, `svgIcon:` 정의 585곳). 사용자가 이 시스템 전체를
도트로 바꾸길 원해서 진행.

### 12-1. 실측으로 바로잡은 착각

처음엔 "585곳의 렌더 지점"이라고 오해했는데, 실제로 grep해보니:
- `svgIcon:` **정의**(데이터) = 585곳
- `.svgIcon` **렌더 참조**(화면에 쓰는 곳) = 겨우 **86곳**

렌더 지점이 훨씬 적다는 걸 정확히 확인하고 나서야 범위를 제대로
잡았다 — 막연한 추정치를 그대로 믿지 않고 직접 재검증한 게 핵심.

### 12-2. 렌더 지점 와이어링 (`wire-svgicon.js`) — 86곳 중 83곳

두 가지 패턴을 안전하게 치환:
- 단순형 `${x.svgIcon||x.icon}` → `getEntityIconHTML(x,{size:16})` 폴백형
- 리사이즈형 `${(x.svgIcon||'').replace('width="20" height="20"','width="N" height="N"')||x.icon}`
  → `getEntityIconHTML(x,{size:N})` (원본 SVG 크기 조절용 문자열
  치환을 `{size:N}` 옵션으로 대체)

`<span`/`<div` 태그 없는 3곳(데이터를 다른 곳에 전달만 하는 코드)은
전과 동일한 안전장치로 자동 제외. **83곳 적용, 26개 파일.**

**핵심 안전성**: `getEntityIconHTML`은 매니페스트에 그 이름이
없으면 그대로 `x.svgIcon||x.icon`(원래 동작)으로 폴백하므로, 이
와이어링 자체는 100% 무위험이다 — 매니페스트에 아직 없는 이름이면
아무것도 안 변하고, 나중에 그 이름이 등록되면(재빌드만으로) 자동으로
이미지가 뜬다.

### 12-3. 새 스캐너 (`scan-svgicon-defs.js`) — 359개 신규 엔티티 발견

기존 `scan-entities.js`는 `src/data/*.js`만 훑는다. 그런데 svgIcon
정의 상당수는 **로직 파일에 직접 박혀 있다**(이 프로젝트의 data/
logic 분리 관례를 따르지 않은 부분) — 예: `progression/020`의
`ELEMENTAL_AWAKENING_STAGES`는 `export const`로 최상위에 있는데도
`src/data/`가 아니라서 기존 스캐너가 절대 못 찾았다.

로직 파일을 실제 모듈로 로드하면(esbuild+vm) window/document 참조
때문에 대부분 실패하므로, 대신 **"항목 하나 = 거의 항상 한 줄"이라는
이 코드베이스 전체의 실측 패턴**을 이용해 텍스트 정규식으로
`name`+`icon`(+선택적 `id`/`rarity`)을 그 줄에서 직접 뽑아냈다 —
실행하지 않고 읽기만 하므로 안전.

- 18개 파일에서 **359개** 새 엔티티 발견(`progression/020` 77개,
  `job/029` 56개, `job/042` 36개, `race/260` 36개, `npc/067`
  34개 등).
- 그룹(같은 배열)별로 badge 모양이 일관되게 유지되도록 소스 컨텍스트
  (파일+배열 변수명)를 그대로 시드에 사용 — 11절의 badge 그룹핑
  로직 재사용.
- **부수적으로 발견**: 9절에서 "구조상 정밀 이미지가 불가능하다"고
  판단했던 `FACTIONS_BY_SCENARIO`(세력)가 사실은 `name` 필드를
  제대로 갖고 있었다(그때는 다른 이유로 못 봤던 듯) — 이번 스캐너로
  34개 세력 전부 정상적으로 이미지가 생겼다. 이전 판단이 틀렸다는
  걸 인정하고 기록.

### 12-4. 검증

- 재생성: 3,450 → **3,806개** 이미지(badge 814 → 1,170), 총 용량
  728.4KB(여전히 1MB 미만).
- Playwright로 5가지 케이스 직접 확인: (1) 이미 스캔돼 있던
  만신전 신격(이그드라 등)이 실제로 이미지로 뜸, (2) 새로 스캔된
  원소각성 단계가 이미지로 뜸, (3) 숨겨진 직업(대마법사)이 이미지로
  뜸, (4) 세력(FACTIONS_BY_SCENARIO)이 이미지로 뜸, (5) 매니페스트에
  없는 이름은 안전하게 원래 이모지로 폴백.
- `renderPantheonPanel()`을 실제로 호출해서 만신전 패널 스크린샷
  촬영 — 손그림 SVG 대신 진짜 도트 흉상 9개가 나열되는 것 확인.
- 전체 회귀 테스트 통과(무관한 네트워크 에러 1건 — 게임의 실제 AI

### 12-5. 사용자가 "미리 보고 결정하겠다"고 한 것 (보류 중)

타이틀 화면/캐릭터 초상화는 원래 게임에 없던 새 화면이라, 만들기

## 13. 6차 라운드 — "다 하자" (타이틀·초상화·지도·농장·NPC관계도 전부)

12절에서 시안만 보여주고 결정 대기 중이던 타이틀 화면/초상화 + 사용자가
그때는 선택 안 했던 월드맵·미니맵·농장 타일·NPC 관계도까지, "다 하자"
한 마디로 전부 진행. 타이틀/초상화는 방향을 다시 안 물어보고 직접
판단해서 골랐다(아래 13-1 참고) — 마음에 안 들면 언제든 다른 시안으로
바꿔달라고 하면 됨.

### 13-1. 타이틀 화면 + 캐릭터 초상화

- **타이틀 화면**: 12절 시안 A(던전 입구, 앰버색)로 결정해서 실제
  `template.html`의 API 키 입력 화면(`#screen-apikey`)에 적용 — 동굴
  지형 타일 배경 + 네 모서리 무기/방패 장식 + 앰버색 글로우 로고.
  **기능(키 입력/시작 버튼)은 전혀 안 건드림**, 배경 장식만 추가.
  라이트 모드에서는 이 던전 아트가 크림톤과 안 어울려서 자동으로
  꺼지고 원래 화면 그대로 나온다(`body.light-mode` 분기).
- **캐릭터 초상화**: 새 UI를 만들지 않고, 이미 있던 원형 금테
  아바타(`char-avatar`/`pc-char-avatar`, 채팅 헤더+PC 사이드패널)를
  실제로 채웠다 — 지금까지 `race.icon`(손그림 SVG)을 그대로 넣고
  있던 자리를 `getEntityIconHTML(race,...)`로 교체. 별도 프레임을
  새로 만들 필요가 없었던 이유: 이 `.avatar` CSS가 이미 정확히 시안에서
  보여준 "원형 메달" 모양이었음.

### 13-2. 부수적으로 발견한 진짜 버그: RACE_DEFS/직업 선택 화면이
지금까지 이미지가 아예 없었다

`char-avatar`를 고치려고 보니, `RACE_DEFS`(종족 12종)의 `icon` 필드
자체가 이모지가 아니라 **손그림 SVG 문자열**이었다(`svgIcon`이 따로
있는 게 아니라 `icon:` 자체가 SVG). 같은 패턴이 `items/004`(장비
슬롯 12종, label+SVG)와 `core/084`의 `BASE_4`(전사/마법사/도적/궁수/
성직자/방랑자 직업 선택, name+SVG)에도 있었다 — 즉 **직업 선택
화면과 장비 빈 슬롯 아이콘은 처음부터 이미지가 생성된 적이 없었다.**

- `scan-svgicon-defs.js`를 확장: `svgIcon:` 필드가 따로 있는 경우뿐
  아니라 **`icon:` 필드 자체가 `<svg`로 시작하는 경우**도 잡아내도록
  했다. 또한 "한 줄에 다 있다"는 기존 가정이 안 맞는 경우(`RACE_DEFS`는
  id/name/icon이 서로 다른 줄에 있음)를 위해 **최근 6줄을 합쳐서
  보는 슬라이딩 윈도우** 방식으로 바꿨다 — 정규식에 `m`(멀티라인)
  플래그를 추가해 `^`가 각 줄 시작에도 매치되게 함.
- 이 확장으로 **37개 신규 엔티티**(종족 12 + 장비슬롯 12 + 직업
  BASE_4 5 등) 추가 발견. `category` 필드가 있으면 그대로 쓰되
  (armor→shield, acc→accessory 정규화), 실제 SHAPES에 없는 값(예:
  `TIER2_JOBS`의 `combat`/`magic`/`stealth` 같은 "전투 계열" 태그)은
  무시하도록 화이트리스트를 추가했다 — 처음엔 이걸 안 걸러서
  `img/combat/`, `img/magic/` 같은 엉뚱한 카테고리 폴더가 생기는
  걸 실측으로 발견하고 고침.

### 13-3. 부수적으로 발견한 진짜 버그: 직업 데이터가 무기/방패로 오분류

`전사`/`도적`/`궁수`같은 직업이 **무기 아이콘**으로 나오고 있었다
(`data/042`의 `BASE_JOBS`, `data/208`의 `JOB_DEFS`) — 원인은
`classify()`가 "atk/weaponType 필드가 있으면 무기"라는 필드 기반
규칙을 "JOB_DEFS 밑에 있으니 인물"이라는 경로 기반 규칙보다 먼저
검사하고 있었기 때문. `scan-entities.js`에 새 규칙을 추가: 부모 키
또는 조부모 키가 JOB/HERO/PANTHEON을 포함하면(단, 중첩된
`.skills`/`.abilities` 같은 하위 배열은 제외하고, `slot` 필드가
있는 진짜 장비는 제외) 무조건 npc로 분류하도록 순서를 앞당김.
적용 후 `전사`/`도적`/`궁수`/`레인저`/`검성`/`대장장이` 등이 전부
정상적으로 인물 흉상 이미지로 바뀐 것을 실측 확인.

## 14. 7차 라운드 — "진짜 다 된거 맞아?"에 답하려고 다시 판 진짜 빈틈

사용자가 "내가 직접 보는 모든 부분에 다 들어가있는 게 맞냐"고 다시
물어서, 이번엔 추측하지 않고 실제로 재검증했다 — 그리고 진짜 빈틈을
또 찾았다.

### 14-1. 발견: 지금까지의 자동 와이어링 도구들이 애초에 못 보는
문법이 있었다

`wire-icons.js`/`wire-icons2.js`/`wire-icons3.js`(1차 버전)는 전부
**템플릿 리터럴**(`` `...${x.icon}...` ``) 문법만 정규식으로 찾고
있었다. 그런데 실측해보니 `<span`/`<div` 태그가 있는 진짜 화면
코드인데도 안 잡히는 게 **82곳** 더 있었고, 원인은 두 가지 완전히
다른 문법이었다:

1. **문자열 접합(concatenation) 스타일**: `'<span>'+x.icon+'</span>'`
   처럼 템플릿 리터럴이 아니라 `+`로 이어붙이는 옛날 방식 — 이
   코드베이스 초반부(특히 `progression/089`, `misc/251`, `ui/097`
   등)에 많이 남아있었다. 정규식이 `${...}` 형태만 찾고 있었으니
   `+` 접합 방식은 애초에 탐지 대상에 없었다.
2. **대괄호 접근(bracket access)**: `CROP_DEFS[cropId]?.icon` —
   기존 정규식의 EXPR 문법이 `.foo`/`?.foo` 체인만 허용하고
   `[...]`는 못 받았다.

### 14-2. `wire-icons3.js` 신규 제작 — 두 문법 다 지원

- EXPR 문법을 `[A-Za-z_$][\w$]*(?:\??\.[A-Za-z_$][\w$]*|\[[^\[\]]{1,80}\])*`
  로 넓혀서 대괄호 접근까지 커버.
- 템플릿(`${...}`)과 접합(`+...+`) 두 스타일 모두, 그리고 각각의
  삼항연산자 변형(`${cond?x.icon:'fb'}`, `+(cond?x.icon:'fb')+`)까지
  4가지 패턴을 전부 정규식으로 매치.
- **버그 발견·수정(직접 발견)**: 1차 버전은 46개 중 44개를 못
  잡았는데, 원인은 EXPR 자체가 `?.icon`까지 통째로 삼켜버려서
  뒤에 오는 명시적 `.icon` 리터럴과 안 맞았기 때문(`stage?.icon`
  같은 흔한 optional-chaining 패턴을 못 잡음). 바깥쪽 `.icon`도
  `\??\.icon`으로 고쳐서 해결.
- **버그 발견·수정 2(직접 발견, 적용 전에 잡음)**: 첫 수정 버전은
  폴백 표현식을 만들 때 `${expr}.icon`처럼 원래 있던 optional
  chaining(`?.`)을 빼먹고 재조립했다 — `S?.character?.icon`같은
  경우 `S?.character.icon`으로 바뀌어서, `S.character`가 없으면
  **오류가 나는 회귀**가 될 뻔했다. 폴백 쪽은 항상 `?.icon`을
  쓰도록 고쳐서(있으나 없으나 안전) 막았다 — 적용 전 프리뷰
  단계에서 직접 비교해서 발견.
- 82곳 중 71곳 자동 변환 적용, 남은 11곳(`.map().join()` 안에
  여러 아이콘을 잇거나, 함수 호출 결과에 바로 `.icon`을 붙이는 등
  정규식으로 안전하게 못 나누는 경우)은 **손으로 하나씩 확인하며
  직접 수정** — 함수 호출 결과는 즉시실행함수(IIFE)로 한 번
  변수에 담은 뒤 연결하는 식으로 안전하게 처리.
- 최종 확인: `<span`/`<div` 태그가 있는 줄 중 `getEntityIconHTML`을
  안 거치는 raw `.icon` 참조 **0개** — grep으로 직접 재확인.

### 14-3. 검증

- 빌드 성공(esbuild가 문법 오류 있으면 바로 실패하므로, 자동/수동
  변환 82곳 전부 문법적으로 안전함을 빌드 자체로 1차 확인).
- `pw_final_regression.js` 통과.
- 4가지 패턴(대괄호 접근/접합 스타일/삼항/`.map().join()`) 각각을
  Playwright로 직접 실행해서 실제 이미지 또는 정상 폴백이 나오는
  것 확인 — 그중 하나(`ELEMENT_DEFS.fire`="화염")는 실제 매니페스트에
  있는 이름이라 진짜 도트 이미지(`img/badge/..._fire_화염.png`)가
  렌더링되는 것까지 확인.
- `getEntityIconHTML(` 호출 지점: 527 → **696개**로 증가.

### 14-4. 남은 한계 (정직하게 기록)

- 이번 재검증은 "`.icon` 참조가 있고 그 줄에 `<span`/`<div`가 있는"
  경우만 훑었다. 만약 여는 태그가 앞 줄에 있고 아이콘 참조가 다음
  줄에 있는 식으로 태그와 아이콘이 서로 다른 줄에 떨어진 코드가
  있다면 이 필터로는 여전히 못 잡는다 — 실측상 이 코드베이스는
  한 항목=한 줄로 몰아쓰는 스타일이 압도적으로 많아서 위험이 낮다고
  판단했지만, 100% 배제는 못 한다.
- SVG `<text>` 안의 이모지(HTML `<img>`를 못 담는 자리)는 이번
  일괄 스캔 대상이 아니었다 — 그건 13절에서 개별적으로(월드맵/
  미니맵/NPC관계도) `<image>` 엘리먼트로 따로 처리했었다.

## 15. 8차 라운드 — "완전 세세하게 나누자" (카테고리 내부 서브타입 분화)

### 15-1. 배경: 사용자의 정곡을 찌르는 질문

14절까지 "화면에 보이는 모든 곳에 도트 이미지가 들어갔다"는 확인이
끝난 뒤, 사용자가 이 툴이 **어떻게 작동하는지** 물어봤다. 답을 하다
보니 스스로도 솔직히 인정해야 했던 한계가 드러났다: 같은 category
(무기/몬스터/방어구/장신구/재료/NPC) 안에서는 실루엣(모양) 자체가
**전부 하나로 고정**돼 있고, 색상(금속색/피부색/등급 색조)만 이름
해시로 달라진다는 것. 즉 "강철검"과 "장검"은 모양이 100% 동일했다.
사용자가 정확히 이 문제("다 비슷비슷하게 나올 수 있잖아")를 짚었고,
"완전세세하게... 나중에도 또 쓸 툴이니까"라며 category 내부를 실제
게임 데이터 신호(무기 종류/장비 슬롯)로 세분화해달라고 요청했다.

### 15-2. 설계: AI 재분석이 아니라 이미 있는 필드 신호를 더 쓴다

이번 확장도 5~14절과 같은 원칙을 지켰다 — **AI 판단을 새로 추가하지
않고, 이미 데이터에 있는 신호(icon 이모지, 장비 slot)를 더 정교하게
읽는다.** 새 신호 두 가지:

1. **무기/몬스터/재료의 `icon` 이모지** — 예: 🏹는 활, 🪓는 도끼,
   🐉는 용, 👻는 유령, 🍖는 고기, 📜는 두루마리. `scan-result.json`을
   직접 집계해서 실제 데이터에서 어떤 이모지가 몇 번 나오는지 먼저
   측정하고(예: 무기 246개 중 ⚔️72+🗡️54+🏹15+🪓15+🔱13+🔨11=180개가
   상위 6개 이모지에 몰림), 빈도 높은 이모지만 표적으로 삼았다 —
   롱테일(나머지 소수 이모지)은 기존 기본 모양으로 안전하게 폴백.
2. **방어구/장신구의 실제 장비 슬롯** — `scan-entities.js`의
   `SLOT_KEY_MAP`(ITEM_POOL 같은 구조에서 부모 키가 곧 슬롯:
   helmet/armor/gloves/boots/cloak/shield, necklace/ring/belt/
   trinket/earring/amulet)이 이미 알고 있던 정보인데, 지금까지는
   "카테고리 분류"에만 쓰고 그 뒤 버렸다. 이번에 그 원본 슬롯 키를
   `entity.slot`으로 스캔 결과에 같이 실어 보내도록 고쳐서(신뢰도
   100%, 필드 기반이라 오분류 여지가 없음) 헬멧/갑옷/장갑/장화/
   망토, 목걸이/귀걸이/벨트를 실루엣부터 구분되게 했다.

### 15-3. 새 실루엣 32종 설계 + 렌더 미리보기로 직접 검증

`generators.js`의 기존 마스크 스타일(16x16 도트, mirrorH로 좌우
쌍둥이 배치하는 관례 — 단, weapon만 원래부터 비대칭 단일 실루엣)을
그대로 따라 32개 신규 실루엣을 손으로 설계했다:
- 무기 6종: 단검/도끼/활/철퇴/삼지창/완드 (기존 검은 그대로 기본값)
- 몬스터 9종: 드래곤/유령/악마/박쥐/골렘/뱀/새/거미/언데드 (기존
  네발짐승은 그대로 기본값)
- 방어구 5종: 투구/갑옷/장갑/장화/망토 (기존 방패는 그대로 기본값)
- 장신구 3종: 목걸이/귀걸이/벨트 (기존 반지 모양은 그대로 기본값)
- 재료 6종: 목재/식물/고기/도자기/동전/두루마리 (기존 광석은 그대로
  기본값)
- NPC 4종: 왕족/마법사/사제/전사 (기존 평민 흉상은 그대로 기본값)

**실제 렌더링 결과를 직접 보면서 반복 수정했다** — 처음 그린 활은
타원(닫힌 고리)처럼 보여서 활 시위가 안 열려 있는 문제를 찾아 곧은
시위 줄을 활 몸통과 분리해서 다시 그렸고, 드래곤/박쥐/새/언데드는
머리만 있고 몸통이 없어서 서로 구분이 안 되는(전부 "뿔 달린 동그라미"
로 보이는) 문제를 발견해서 몸통/다리/날개를 16행 전체에 걸쳐 채우도록
다시 그렸다. 사제(cleric)도 처음엔 후광 표시가 너무 은은해서 기본
NPC와 구분이 안 됐는데, 얼굴 전체를 감싸는 두건(hood) 실루엣으로
바꿔서 마법사(뾰족모자)/전사(투구)/왕족(왕관+머리카락)과 확실히
구분되게 했다. **이 반복 수정은 전부 실제 파일을 고치기 전에
스크래치패드에서 미리보기 PNG를 직접 렌더링해서 눈으로 보고
확인한 것** — 이전 라운드들의 "적용 전 프리뷰로 검증" 원칙을 색상
버그가 아니라 그림 자체의 가독성에도 적용한 셈이다.

### 15-4. 안전한 폴백 구조 (`resolveShapeKey`)

`generateIcon()`에 `resolveShapeKey(category, entity)` 함수를
추가했다 — entity의 icon/slot을 보고 해당하는 세부 실루엣 키를
찾고, **못 찾으면 무조건 기존 category 기본 모양으로 그대로
폴백**한다. 즉 이 표에 없는 나머지 항목들은 지금까지와 완전히
똑같이 동작한다 — 이번 확장으로 인해 기존에 잘 나오던 항목이
깨지거나 바뀔 위험이 없다.

## 16. 9차 라운드 — AI 이미지 생성 + 강제 도트 양자화 파이프라인 (골격 완성, API 키 대기)

### 16-1. 배경

15절까지도 여전히 "같은 카테고리 안에서는 실루엣이 한정된 템플릿"
이라는 한계가 남아있었다. 사용자가 실제로 "화염 속성 장검/얼음 마법
지팡이/숲의 정령 몬스터" 3개를 직접 테스트해보자고 제안 → 지금
시스템으로 렌더링해보니 세 가지 문제가 실측으로 드러났다: (1) "화염"/
"얼음"이라는 텍스트 의미 자체를 전혀 못 읽어서 색조차 안 바뀜, (2)
같은 아이템이라도 데이터에 어떤 이모지가 들어있냐에 따라 결과가
완전히 달라지는 불안정함(예: ❄️로 넣으면 지팡이인데 검 모양이 나옴),
(3) "숲의 정령"처럼 대응하는 실루엣 자체가 없는 개념은 엉뚱한 모양
(네발짐승)으로 나옴. 이 세 문제는 규칙 기반 시스템의 구조적 한계라
서, 진짜 AI(이미지 생성)가 필요하다는 결론에 도달했다.

### 16-2. 핵심 원칙: "AI는 그리고, 툴은 도트로 강제 변환"

사용자가 정확히 짚은 우려("AI가 만든 도트모양 이미지를 그냥 넣는
거 아니냐, 용량 차이가 심할텐데") — 이게 핵심 설계 제약이 됐다.
AI 원본(큰 해상도, 자유 색상)은 **절대 그대로 저장되지 않는다.**
반드시 아래 변환을 거친 결과만 디스크에 쓰인다:
1. AI 이미지 생성 API 호출 → 큰 원본(예: 1024x1024) 받음(메모리에만)
2. 박스 필터로 작은 고정 그리드(32x32)로 다운스케일
3. median-cut 색상 양자화로 팔레트를 16색 정도로 강제 압축
4. **기존에 이미 만들어둔 `png-encoder.js`(인덱스 컬러 PNG 인코더)**로
   재인코딩 — 절차적 생성기와 정확히 같은 포맷/용량대

### 16-3. 새로 만든 파일

- **`pixelate.js`**: 위 2~4단계(디코딩은 `pngjs`, 박스 다운스케일,
  median-cut 양자화)를 구현. `pixelateToIndexed(pngBuffer, opts)`가
  `generateIcon()`과 완전히 같은 `{width, height, indices, palette}`
  형태를 돌려줘서, 호출부는 소스가 AI든 절차적 생성이든 이후 처리가
  100% 동일하다.
- **`ai-image-gen.js`**: Gemini 이미지 생성 API(`gemini-2.0-flash-
  preview-image-generation`, 게임 본체가 이미 쓰는 것과 같은
  `generativelanguage.googleapis.com` 엔드포인트) 호출 전담. 키는
  `process.env.GEMINI_API_KEY`로만 받고 코드/로그 어디에도 남기지
  않는다. 프롬프트는 일부러 "flat color, no gradient, no shadow,
  simple silhouette, plain white background" 식으로 강하게 제한 —
  안 그러면 다운스케일+양자화가 지저분하게 뭉개짐(사진 같은 원본은
  아무리 양자화해도 얼룩덜룩해짐). 실패하거나 키가 없으면 무조건
  `null` 반환 → 호출부가 절차적 생성기로 자동 대체(회귀 위험 없음).

### 16-4. `generate.js` 통합 (하위호환 유지)

- `--ai` 플래그로 켬(기본은 꺼짐 — 안 켜면 지금까지와 100% 동일하게
  작동, 실측으로 재확인: 3854개/730.9KB로 변경 전과 완전히 동일).
- `--ai-limit=N`(기본 10): 이번 실행에서 **새로** API를 부를 최대
  개수. 이미 `ai-cache-raw/`에 캐시된 항목은 이 한도에 안 잡히고
  재사용만 함 — 3,450개를 한 번에 다 돌릴 필요 없이 여러 번에 걸쳐
  나눠서(그리고 중간에 멈췄다 이어서) 채울 수 있다.
- `--ai-only=weapon,monster`: 특정 카테고리만 대상으로 삼는 테스트용
  필터.
- AI 원본(`ai-cache-raw/*.png`, 큰 파일)은 배포 zip에 포함 안 함 —
  나중에 양자화 파라미터(색상 수 등)를 바꾸고 싶을 때 API를 다시
  안 불러도 재변환할 수 있게 남겨두는 로컬 캐시일 뿐.
- 게임 코드(`getEntityIconHTML`, 매니페스트 조회 696곳)는 **전혀
  안 건드림** — 이미지가 절차적으로 만들어졌든 AI로 만들어졌든
  매니페스트 형식이 같아서 구분할 필요가 없다.

### 16-5. 검증 (API 키 없이 할 수 있는 데까지)

- **다운스케일+양자화 파이프라인만 독립적으로 검증**: 진짜 AI 이미지가
  없어서, "AI가 그릴 법한 부드러운 그라데이션+안티앨리어싱" 특성을
  흉내낸 합성 테스트 이미지(사과 모양, 256x256, 부드러운 원+그림자)를
  직접 만들어서 16/32/64 세 가지 그리드 크기로 변환해봄 — 결과:
  안티앨리어싱이 완전히 제거되고 색상이 몇 단계로 딱 떨어지는 계단식
  음영으로 정리된 진짜 도트 이미지가 나옴, 파일 크기도 223~447바이트
  (절차적 생성기 결과물과 동급).
- `--ai --ai-limit=3 --ai-only=weapon`으로 실제 `generate.js`를
  돌려서 키 없을 때 정상적으로 3개 다 절차적 생성으로 자동 대체되고
  크래시 없이 끝까지 도는 것 확인, 최종 결과물이 AI 옵션 없이 돌린
  것과 완전히 동일(3854개/730.9KB)한 것도 재확인.
- 빌드(`node build.js`) + `pw_final_regression.js` 통과(기존과 동일,
  무관한 Gemini 인증서 오류만 있음).
- **아직 못 한 것**: 진짜 AI가 그린 이미지로 끝까지 돌리는 실전
  테스트 — 사용자가 무료 요금제 API 키를 나중에 주기로 함. 키를
  받으면 `GEMINI_API_KEY=<키> node tools/pixelart-gen/generate.js
  --ai --ai-limit=5` 처럼 소량으로 먼저 돌려서 실제 결과물 품질을
  확인하고, 괜찮으면 `--ai-limit`을 늘려가며 나머지를 채우면 된다.

### 16-5-1. 품질 파라미터 상향 조정

사용자가 처음 결과 설명을 듣고 "80년대 게임 같다"고 지적 — 실측해보니
정확한 지적이었다. 초기 기본값(`gridSize:32, maxColors:16`)은 합성
테스트 이미지 기준 341바이트로, 부드러운 그림자/하이라이트가 거친
계단으로 뭉개짐. `gridSize:48/maxColors:32`(544바이트), `gridSize:64/
maxColors:48`(906바이트) 세 단계로 직접 렌더링해서 비교한 결과, 64/48
설정에서 하이라이트 반사광까지 살아있는 "요즘 인디게임 도트아트"
수준이 나옴을 확인. 장당 1KB가 안 되는 차이라(3,450개 전부 합쳐도
~3MB, 게임 전체 10MB 대비 미미) 기본값을 `gridSize:64, maxColors:48`
로 올림(`pixelate.js`/`generate.js` 양쪽 다 수정) — 여전히
안티앨리어싱 없는 진짜 인덱스 컬러 도트라는 본질은 그대로, 격자
크기/색상 수만 다이얼처럼 조절 가능한 파라미터임을 확인.

### 16-6. 남은 할 일 / 알려진 리스크

- 실제 Gemini 이미지 생성 응답 스키마(`candidates[0].content.parts[].
  inlineData`)는 문서 기준으로 작성한 것이라, 실제 키로 첫 호출을
  해봐야 그대로 맞는지 확인 가능 — 안 맞으면 `ai-image-gen.js`의
  파싱 부분만 살짝 고치면 됨(다른 부분엔 영향 없음).
- 무료 요금제는 레이트리밋이 있을 수 있어서, 대량 실행 시
  `--ai-limit`을 작게 잡고 여러 번 나눠 돌리는 걸 권장.
- 프롬프트가 "flat color, no gradient"를 강하게 요구해도 모델이
  100% 따르진 않을 수 있음 — 실제 결과물을 보고 프롬프트나 양자화
  파라미터(`maxColors`, `alphaThreshold`)를 조정해야 할 수 있음.

## 17. 10차 라운드 — 이미지 생성(유료) 대신 텍스트 분석(무료)으로 우회

### 17-1. 배경: 이미지 생성은 결제 계정이 필요하다는 게 실측으로 확인됨

16절의 골격을 실제 키로 테스트하면서 **여러 겹의 디버깅 삽질**을
거쳤다(자세한 기록은 아래 17-2). 최종 결론: 이 계정/무료 티어에서
**텍스트 생성은 정상 작동하지만 이미지 생성 모델은 전부 할당량 0**
(결제 계정 연결 안 하면 아예 접근 불가, 사용량 문제가 아니라 정책
자체)이라는 게 실제 API 응답으로 확인됨. 사용자가 "그럼 무료로는
이 툴을 못 돌린다는 소리네?"라고 확인 → 맞다고 답함. 이어서 사용자가
"그러면 분석은 못해? 사실 분석만 제대로 하면 이미지는 크게 다르지
않을거 아냐"라고 제안 — **텍스트 분석(무료)으로 종류/속성색을
판단해서 절차적 생성기(무료)에 넘기는 방식**을 즉석에서 제안했고,
정확히 맞는 방향이라 바로 구현·검증까지 했다.

### 17-2. 디버깅 과정에서 있었던 실수들(정직하게 기록)

실제 키로 테스트하면서 총 4단계 삽질이 있었다 — 전부 기록해둔다,
나중에 비슷한 문제 겪을 때 참고하려고:
1. 처음 두 번은 `AQ.Ab8R...`로 시작하는 키를 "이건 Gemini 키가 아니라
   다른 종류의 토큰"이라고 잘못 판단해서 사용자에게 엉뚱하게
   `AIzaSy...` 형식을 다시 발급받으라고 안내함 — **틀린 안내였다.**
   실제로는 2026-09부로 구글이 신규 키를 전부 `AQ.` 형식으로만
   발급하도록 바꿨고, 레거시 `AIzaSy` 형식은 더 이상 발급 안 됨.
2. `AQ.` 형식 키는 `?key=` 쿼리 파라미터가 아니라 `x-goog-api-key`
   HTTP 헤더로 보내야 인증되는 것까지는 웹 검색으로 정확히 찾아서
   고쳤는데도 계속 "API key not valid"가 남 — 원인은 **bash 명령어
   문법 실수**였다: `node -e "..." GEMINI_API_KEY=값` 처럼 환경변수
   할당을 명령어 뒤에 쓰면 실제로는 환경변수가 아니라 그냥 문자열
   인자로 들어가서 `process.env.GEMINI_API_KEY`가 계속 비어있었다
   (`VAR=값 command`처럼 명령어 **앞**에 와야 환경변수로 적용됨).
   이것 때문에 사용자에게 "결제 계정 확인해보라"는 엉뚱한 요청까지
   했었다 — 사용자가 "내가 너를 학습시켜야 되냐"고 정당하게
   지적했고, 명령어를 바로잡고 나서야 진짜 원인(아래 3, 4번)이
   드러났다.
3. 문법을 고치고 나니 진짜 원인 하나 발견: 모델명
   `gemini-2.0-flash-preview-image-generation`이 **단종된 모델**
   (404). `ListModels` API로 실제 사용 가능한 58개 모델 목록을
   직접 조회해서 최신 이미지 모델들(`gemini-2.5-flash-image`,
   `gemini-3.1-flash-image` 등)을 찾아냄.
4. 최신 모델명으로도 이미지 생성 모델은 전부 429(할당량 0)로 거부 —
   반면 텍스트 모델(`gemini-2.5-flash`)은 정상 호출됨. 이걸로
   "이미지 생성만 결제 계정 필요"라는 최종 결론을 확정함.

### 17-3. 새 설계: `ai-analyze.js` — 텍스트로 "분석"만, 그림은 여전히 절차적 생성기

- 무료 텍스트 모델(`gemini-3.1-flash-lite` — 사용자가 실제 요금제
  화면 스크린샷에서 RPD 500/일로 가장 여유 있는 모델을 직접 골라줌)
  에 이름+설명을 주고, **정해진 enum 값만** 고르게 강제한다
  (Gemini의 `responseSchema` 기능으로 강제 — 무기 종류 7개 중 하나,
  속성색 8개 중 하나. 모델이 이상한 값을 뱉을 수가 없는 구조).
- 결과(`{subtype, element}`)를 `generateIcon()`에 넘기면:
  - `entity.aiSubtype`이 있고 그게 `SHAPES`에 있는 키면 icon/slot
    기반 추측(`resolveShapeKey`)보다 우선 사용.
  - `entity.element`가 있으면 `ELEMENT_HUE` 표(fire=12,ice=195,
    poison=110,holy=48,dark=265,nature=100,electric=55)로 등급
    색조 대신 그 색조를 쓴다 — `rarityPalette(rarity, hueOverride)`
    로 확장해서, **등급별 밝기 단계는 그대로 유지한 채(전설급 화염이
    일반급 화염보다 화려하게) 색상 자체만 테마색으로 교체**되게 함.
  - 둘 다 없거나 유효하지 않으면 기존 로직 그대로 — 100% 하위호환.
- 실패해도 항상 `{subtype:null, element:'none'}`으로 안전 폴백(API
  키 없음/네트워크 오류/파싱 실패 전부 이 경로로 수렴).

### 17-4. `generate.js` 통합

- `--analyze` 플래그(기본 꺼짐, 100% 하위호환 재확인함 — 껐을 때
  총 용량 730.9KB로 변경 전과 완전 동일).
- `--analyze-limit=N`(기본 40), `--analyze-only=weapon,monster`
  — `--ai`와 같은 패턴.
- 분석 결과는 `ai-analyze-cache.json`에 캐시(작은 텍스트라 배포 zip에
  포함해도 무해 — AI 원본 이미지 캐시와 달리 용량 문제 없음).
- 호출 사이 4.5초 간격을 둬서 무료 티어 분당 한도(RPM) 보호.

### 17-5. 검증

- 실제 게임 데이터 3개(`wp_001` 낡은 단검, `wp_002` 나무 몽둥이,
  `wp_003` 녹슨 검)로 `--analyze --analyze-limit=3 --analyze-only=
  weapon` 실행 → 단검/철퇴(몽둥이→mace로 합리적 매핑)/검으로 정확히
  분류되고, 셋 다 속성 없는 평범한 무기라 element:'none'으로 정확히
  판단(허위 속성 부여 없음 확인).
- 사용자가 준 3개 예시(화염 속성 장검/얼음 마법 지팡이/숲의 정령)로
  실제 렌더링 결과 확인: 화염 장검이 진짜 붉은색으로, 얼음 지팡이가
  진짜 파란색으로, 숲의 정령이 초록색+유령 실루엣으로 나옴 — 8차
  라운드에서 텍스트 의미를 못 읽던 문제가 완전히(그리고 무료로)
  해결됨.
- 빌드 + `pw_final_regression.js` 통과(기존과 동일).

## 18. 11차 라운드 — "완전 무료 자동화" 요청 → Pollinations 무료 백엔드 연결

### 18-1. 배경

사용자가 "오래 걸려도 무료로 하고 싶다, 이미지 생성까지"라고 명확히
요청 → Gemini 이미지 생성(유료) 대신 API 키가 아예 필요 없는 무료
공개 이미지 생성 서비스(Pollinations.ai)를 대안으로 제시하고 연결함.
이어서 사용자가 "게임파일을 넣으면 구글 API가 분석하고 → Pollinations
에 요청해서 이미지를 만들고 → 그걸로 도트를 찍어서 → 게임파일에
자동으로 대입까지" 하는 완전 자동화 툴이 맞냐고 확인 → 정확히 그
그림이 맞다고 확인하고 실제로 그렇게 연결했다.

### 18-2. 이 세션 자체의 네트워크 제약 발견

Pollinations를 테스트하려다 이 클라우드 작업 환경 자체가 허용
목록에 없는 외부 호스트로는 못 나가게 막혀있다는 걸 발견함
(`image.pollinations.ai`, `api-inference.huggingface.co` 둘 다
403/DNS 실패로 차단 확인 — 반면 구글 API 호스트는 예외적으로 뚫려
있어서 그동안 Gemini 호출은 됐던 것). 이건 이 세션의 보안 정책이라
우회하면 안 되는 부분이라 정직하게 알림 — **코드는 정확히 만들어서
드리되, 실제 Pollinations 호출이 잘 되는지는 사용자 컴퓨터(네트워크
제한 없는 환경)에서 직접 검증해야 한다**는 점을 명시함.

### 18-3. `ai-image-gen.js`를 프로바이더 2종 지원으로 재작성

- 기본값: **Pollinations**(무료, 키 불필요, `IMAGE_PROVIDER` 환경변수
  생략 시 자동 선택). `IMAGE_PROVIDER=gemini`를 명시할 때만 유료
  Gemini 경로로 감(이전 라운드에서 발견한 단종 모델명도 이 김에
  `gemini-2.5-flash-image`로 고쳐둠 — 장당 약 $0.039, 참고용).
- `buildPrompt()`가 `entity.aiSubtype`/`entity.element`(무료 텍스트
  분석 결과)를 프롬프트에 자동으로 녹여 넣도록 확장 — "이건 구체적으로
  ~다", "색 테마는 ~다" 같은 문장을 추가해서, 이미지 생성 자체도
  분석 결과를 반영하게 만듦.
- 결정론적 시드(이름 해시 기반)를 Pollinations의 `seed` 파라미터로
  넘겨서, 같은 항목은 재생성해도 같은 그림이 나오게 함(기존 절차적
  생성기의 "이름→항상 같은 결과" 원칙과 동일하게 맞춤).

### 18-4. `generate.js`: `--ai` 하나로 전체 파이프라인 자동 연결

- `--ai`만 켜도(별도 `--analyze` 없이) 내부적으로 무료 텍스트 분석을
  같이 돌리도록 트리거 조건 확장(`NEED_ANALYZE = ANALYZE_MODE ||
  AI_MODE`) — 그 분석 결과가 그대로 이미지 생성 프롬프트에 들어가고,
  이미지 생성이 실패해도(또는 GEMINI_API_KEY가 없어도) 분석 결과만은
  절차적 생성기 쪽에 반영돼서 헛되지 않음.
- 요약: **"게임 데이터 스캔 → (무료)이름 분석 → (무료)Pollinations
  이미지 생성 → 강제 도트 변환 → 매니페스트 자동 등록"이 `node
  generate.js --ai` 한 줄로 전부 자동 연결됨.**

### 18-5. 발견·수정한 진짜 버그: fetch 타임아웃 없음

실제 키로 통합 테스트하다가 명령어가 120초를 넘겨도 첫 로그 한 줄도
안 찍히는 걸 보고 "네트워크가 막힌 곳에 걸리면 fetch()가 무한정
기다릴 수 있다"는 실제 위험을 발견 — 타임아웃이 없으면 3,450개 중
막힌 항목 하나가 배치 전체를 영영 멈추게 할 수 있는 구조였다.
`AbortController` 기반 강제 타임아웃(25초)을 이미지 생성 2종(Pollinations/
Gemini)과 텍스트 분석 호출 전부에 추가해서, 막힌 항목은 반드시
실패로 처리되고 절차적 생성으로 넘어가게 고쳤다. (재현: 이후 재시도에서
Pollinations가 실제로는 403을 빠르게 돌려줘서 이 특정 실행에서
타임아웃이 실제로 발동하진 않았지만, 방어 코드 자체는 실제 위험을
막는 정당한 수정이라 그대로 유지.)

### 18-6. 검증

- `--ai --ai-limit=2 --ai-only=weapon --analyze-limit=2 --analyze-only=
  weapon`로 실제 키를 넣고 실행 → 분석 2건 성공(무료), Pollinations
  이미지 생성 2건은 이 환경의 네트워크 정책 때문에 403으로 실패 →
  둘 다 정상적으로 절차적 생성으로 폴백, 크래시 없음, 최종 용량도
  변경 전과 동일(730.9KB)하게 안전하게 끝남.
- 플래그 없이 재실행 → 완전히 동일한 기존 동작 재확인.
- 빌드 + `pw_final_regression.js` 통과.
- **아직 못 한 것**: Pollinations로 실제 이미지가 생성되는지 자체는
  이 세션에서 검증 불가(네트워크 정책) — 사용자가 본인 컴퓨터에서
  `node tools/pixelart-gen/generate.js --ai` 실행해서 직접 확인
  필요.

## 19. 12차 라운드 — 구도(클로즈업 vs 전신) 자동 검증

### 19-1. 배경

사용자가 "용"을 검색했을 때 나온 실제 예시 2장을 보여줌 — 하나는
머리/목만 크게 확대된 구도, 하나는 몸 전체(S자 형태)가 다 보이는
구도. 이미지 생성 API/서비스는 같은 프롬프트를 줘도 이렇게 구도가
들쭉날쭉하게 나올 수 있는데, 아이콘 세트 전체의 시각적 일관성이
깨지는 문제라 "이런 차이를 AI가 구분할 수 있냐"고 질문함.

### 19-2. 핵심 통찰: "이미지를 읽는 것"은 "이미지를 만드는 것"과 다른 할당량

이미지 생성(output이 이미지)은 결제 계정이 필요했지만, **이미지를
입력으로 주고 텍스트로 답을 받는 것(vision 분석)은 별개의 훨씬 흔한
기능이라 무료 티어에서 될 가능성**을 떠올려서 직접 테스트 — 실측으로
확인됨(200 OK, 정상 응답, 이미지 생성 전용 할당량과 무관). 합성
테스트 이미지(전신이 다 보이는 구도)로 실제 판별시켜보니 "full"로
정확히 답함.

### 19-3. 구현: 생성 → 검증 → (필요시) 1회 재시도 → 그래도 안 되면 절차적 생성 폴백

- `ai-image-gen.js`에 `isFullBodyShot(pngBuffer)` 추가 — 무료
  vision 분석(`gemini-3.1-flash-lite`)에 생성된 이미지를 다시 넣어서
  "full" 또는 "closeup"으로 판정받음. API 키가 없거나 호출이
  실패하면 안전하게 "통과"로 처리(재시도 낭비 방지, 구도 검증은
  "있으면 좋은" 품질 개선이지 필수 관문이 아니므로).
- `buildPrompt()`에 애초부터 "전신/와이드샷, 클로즈업 금지" 문구를
  기본으로 넣어서 애초에 클로즈업이 덜 나오게 하고, 그래도 클로즈업
  판정되면 `_forceWide` 플래그로 더 강한 문구를 추가해 재시도.
- Pollinations는 같은 프롬프트+시드면 같은 그림을 주므로, 재시도 때는
  시드도 다르게 바꿔서(`seedFor()`에 `:retry` 접미사) 진짜 다른 그림이
  나오게 함.
- 재시도까지 실패하면 `null` 반환 → 기존과 동일하게 절차적 생성으로
  안전하게 대체(잘못된 구도의 이미지를 그대로 쓰지 않음).

### 19-4. 검증

- 합성 테스트 이미지(전신 S자 구도)로 `isFullBodyShot()` 직접 호출
  → "full"로 정확히 판정, 함수가 `true` 반환 확인.
- (클로즈업 판정 자체는 합성 테스트 이미지가 추상적인 원 도형이라
  모델이 "N/A"로 애매하게 답해서 이번엔 명확히 재현 못 함 — 안전
  기본값("애매하면 통과")이 의도대로 작동한 것으로 해석. 실제 AI가
  그린 진짜 클로즈업 이미지로는 더 명확하게 구분될 것으로 예상되나,
  이 세션의 네트워크 제약(18절)으로 실제 이미지 생성 자체를 못 해봐서
  실물로는 재검증 못 함 — 사용자가 본인 환경에서 돌릴 때 실제로
  확인 필요.)
- 빌드 + `pw_final_regression.js` 통과, 플래그 없는 기존 실행도
  730.9KB로 동일하게 재확인.

## 20. 13차 라운드 — 수동 지정(manual-overrides.json) + 캐시 영속성 확인

### 20-1. 배경

사용자가 두 가지를 확인/요청: (1) "꺼도 켜도 캐시가 유지되냐" —
그렇다고 확인(`ai-cache-raw/`, `ai-analyze-cache.json`, 최종
`src/assets/img/` 전부 일반 파일이라 디스크에 계속 남음. 단,
지금까지 전달한 zip에는 `ai-cache-raw/`를 일부러 안 넣었으니, 그건
사용자 컴퓨터에서 `--ai`를 처음 돌리는 순간부터 그 컴퓨터에 쌓이는
것이라고 정확히 안내함). (2) "세부적으로 내가 지정해서 만들어달라고
할 수 있냐" — 이건 안 되는 상태였어서 바로 기능을 추가함.

### 20-2. `manual-overrides.json` 신규 추가

- entity id 또는 정확한 이름을 키로, `{subtype, element}`(자동 분석
  대신 쓸 값) 또는 `{prompt}`(이미지 생성 프롬프트 전체를 완전히
  수동으로 대체)를 적어두면, 그 항목은 **AI 텍스트 분석 호출 자체를
  건너뛰고** 사용자가 적은 값을 그대로 씀.
- `generate.js`의 `tryAnalyze()`가 제일 먼저 이 표를 확인하도록
  배치 — `NEED_ANALYZE`(즉 `--ai`나 `--analyze`) 여부와 무관하게
  항상 먼저 체크되므로, **API 키가 전혀 없어도, `--ai` 없이 순수
  절차적 생성만 돌릴 때도 수동 지정이 그대로 적용됨**(부수 효과지만
  유용한 특성이라 그대로 살려둠).
- `ai-image-gen.js`의 `buildPrompt()`도 `entity.promptOverride`가
  있으면 자동 조합 문구를 전혀 안 붙이고 그 문자열을 그대로 씀 —
  완전한 수동 제어.
- 파일이 없거나 JSON 문법이 깨져도 그냥 빈 표로 취급하고 계속
  진행(수동 지정 없이도 항상 정상 동작해야 하므로 방어적으로 처리).

### 20-3. 검증

- `wp_001`("낡은 단검")을 `{subtype:'trident', element:'holy'}`로
  수동 지정 → API 호출 전혀 없이(순수 절차적 생성기만으로) 실제로
  금색 삼지창 이미지가 나오는 것을 실물 PNG로 직접 확인.
- 원상복구 후 재빌드 + `pw_final_regression.js` 통과, 플래그 없는
  기존 실행도 730.9KB로 동일하게 재확인.

## 10. 새 세션/다른 프로젝트에서 이 툴을 다시 쓸 때

1. 이 폴더(`pixelart-gen/`) 전체를 새 프로젝트로 복사.
2. `generators.js`의 `SHAPES`/`TERRAIN_SHAPES`를 새 게임 장르에 맞게
   교체하거나 카테고리 추가.
3. 그 게임의 데이터 구조에 맞는 `scan-entities.js`를 새로 작성
   (기존 걸 참고용 템플릿으로 활용 가능).
4. `generate.js`는 대부분 그대로 재사용 가능(스캐너가 뱉는 표준
   `{id, name, category, rarity, type}` 형태만 맞으면 됨).
