# taleforge_graphic 작업메모장

> 이 파일은 `tools/pixelart-gen/메모장.md`와 같은 성격 — 이 하위 도구만의
> "왜/어떻게" 기록. `작업메모장.md`(루트, memo-gate 훅 대상)는 이 도구에
> 대한 요약만 담고, 자세한 경위는 여기에 둔다.

## 1. 신설 — "ComfyUI를 직접 안 만지고 쓰는" Gradio 화면 (2026-10-28)

### 1-1. 배경

별도로 열린 "TaleForge — 그래픽 생성" 세션에서, 타일포지를 Fable(설계)→
Opus(구현) 경로로 완전히 새로 리디자인하는 프로젝트의 비주얼 에셋을
"Emberville" 레퍼런스(탑뷰 픽셀아트, 디테일한 타일, 동적 조명/파티클,
디아블로×스타듀밸리 톤)로 실험하는 작업 중, 사용자가 "ComfyUI가 여러
가지 연결하고 그런 식이라 직접 쓰기 힘들다"며 본인이 이미 만들어 쓰던
`simple ui confirm`(인물 사진 생성·LoRA 학습 전용 Gradio 앱, ComfyUI를
감싼 "쉬운 화면")을 참고해서 같은 틀로 "taleforge_graphic"을 만들어
달라고 요청.

### 1-2. 구현 전 조사 — 두 차례 zip 확인

①1차 zip(`simple_ui_confirm_c179.zip`)에는 `master.py`/`promptflow.py`/
`geminiapi.py`/`paths.py`/`qsheet.py`/`organizer.py`/`storage.py`/
`history.py`/`expand.py`만 있었는데, 실제 화면(`ui.py`)과 ComfyUI 호출
핵심 로직, 데이터(`prompts.py`), 실행기(`launcher.py`)가 빠져 있었다.
읽어본 결과 **이 도구 자체가 "한국인 미인 스타일" 인물 사진을 AI로
생성하고 LoRA로 학습하는 성인 콘텐츠 전용 도구**(얼굴상/몸매/가슴/허리/
엉덩이 태깅, "Sexy 모드", 란제리/비키니 복장 프리셋, `check_adult.py`
등)임을 확인 — 사용자에게 투명하게 보고하고, 그대로 리네임하는 대신
"쓸 건 쓰고 버릴 건 버리는" 방향을 제안했다. 사용자가 "그게 내가
말한 그거다, 알아서 쓸 거 쓰고 버릴 거 버리고 바꿔서 달라"고 확인.

②2차 zip(`simple_ui_confirm_c180.zip`)에서 빠졌던 3개 핵심 파일
(`ui.py` 9,481줄, `launcher.py` 493줄, `prompts.py` 4,226줄) +
`trainer.py`(3,425줄)·`downloader.py`(1,102줄)·`HANDOFF.md`(1,238줄)·
"왜_이렇게_만들었나.txt"(734줄, 이전 세션이 "내가 반복한 잘못"까지
정직하게 적어둔 회고 문서)까지 전부 받음 — 총 25,648줄. 전부 읽지
않고 구조적으로 필요한 부분만 발췌:
- `왜_이렇게_만들었나.txt`: 이 도구의 설계 철학과 반성 전체(①왜 ②판단
  ③확인한 것 ④지금 평가 4단 구조) — "연결이 맞다는 것과 그림이 좋다는
  것은 다르다"는 핵심 교훈을 그대로 이어받기로 함(아래 1-5번 참고).
- `launcher.py`: GPU 확인→venv→PyTorch(cu128)→ComfyUI 자동 다운로드·
  설치→모델 확인→ComfyUI 백그라운드 실행→준비되면 화면 실행, 이미
  켜진 ComfyUI가 있으면(`comfy_alive()`) 재사용하는 패턴 확인.
- `ui.py`의 `queue_prompt`/`poll_history`/`fetch_image`/`comfy_state`/
  `friendly_error` — ComfyUI와의 "큐 등록→폴링→다운로드" 왕복을
  실전에서 다듬어 온 로직(타임아웃 vs 연결거부를 구분해 다른 재시도
  한도를 주는 것, 영어 오류 원문을 한글로 풀어주는 규칙표 등).
- `run_txt2img`(`ui.py` 4558번째 줄)은 얼굴 고정/ControlNet/스타일
  참조/LoRA 3슬롯/초안 모드 등 완전히 인물 전용이라 포팅 대상에서
  제외 — 실제 그래프를 만드는 `wf_image()` 자체는 읽지 않음(인물
  전용 노드 구성이라 어차피 재사용 불가, 읽을 가치 낮다고 판단).

### 1-3. 확정한 설계 — "재사용(틀)" vs "새로 작성(내용)" 분리

**그대로/거의 그대로 가져온 것(일반 로직, 콘텐츠 무관)**:
- ComfyUI HTTP 왕복 패턴(`comfy_client.py`) — `queue_prompt`/
  `poll_history`(타임아웃 120회/연결거부 30회로 다른 재시도 한도)/
  `fetch_image_bytes`/`comfy_state`/`friendly_error`. 학습 중 생성
  차단(`trainer.generation_block_message`) 같은 이 도구 전용 로직만
  뺐다.
- `get_checkpoints()`/`get_loras()` 신설 — ComfyUI의 `/object_info`
  엔드포인트로 실제 설치된 체크포인트/LoRA 목록을 가져오는 방식은
  원본에 명시적 함수로 없었지만(모델 목록 갱신 로직이 `ui.py` 다른
  곳에 흩어져 있어 포팅 안 함), 같은 "ComfyUI가 보는 것과 항상
  일치" 원칙으로 새로 작성.

**완전히 새로 작성한 것(이 도구만의 내용)**:
- `workflow.py`의 `CATEGORY_PRESETS`/`STYLE_BASE` — 인물 프롬프트
  조립 로직(`promptflow.py`, `prompts.py`) 대신, 사용자가 보내준
  Emberville 스크린샷 2장에서 직접 읽은 스타일 문구(디더링된 질감·
  그림자, 어둡고 채도 낮은 팔레트+포인트 컬러 대비, 동적 조명 glow,
  "Stardew Valley x Diablo" 톤)로 새로 작성. `tools/pixelart-gen/
  ai-image-gen.js`의 `buildPrompt()`(78번 라운드, 타일포지 UI 아이콘
  전용 — 흰 배경·평면·그림자 없음)와 정반대 방향이라 공용화하지 않고
  따로 둠(그쪽은 "UI 아이콘", 이쪽은 "장면/타일/스프라이트").
- 그래프 빌더(`build_workflow`)는 `ai-image-gen.js`의
  `buildComfyWorkflow()`(78번 라운드)와 노드 구성은 사실상 동일
  (CheckpointLoaderSimple→EmptyLatentImage+CLIPTextEncode 긍정/부정→
  KSampler→VAEDecode→SaveImage, LoRA 선택 시 LoraLoader 재배선) —
  이건 ComfyUI 표준 패턴을 둘 다 따른 자연스러운 수렴이지, 코드를
  복사한 게 아니다.
- `ui.py`(Gradio 화면) — 원본의 수백 개 컨트롤(얼굴 고정/ControlNet/
  스타일 참조/LoRA 3슬롯/마스터 LoRA 꼬리표/초안 모드/Hires-fix 등)을
  전부 걷어내고, "카테고리 선택→설명 입력→체크포인트 선택→미리보기
  생성→(마음에 들면) 픽셀아트로 저장" 한 화면짜리로 완전히 새로 설계.
  `pixelate.js` 변환 단계(그리드 크기/색상 수 슬라이더)를 화면에 직접
  노출한 것도 원본엔 없던 이 도구만의 요소(원본은 "진짜 사진처럼"이
  목표라 도트화 개념 자체가 없음).
- `pixelate_bridge.py` — 기존 `tools/pixelart-gen/pixelate.js`를
  파이썬에서 subprocess로 호출하는 다리. 양자화 로직을 파이썬으로
  재구현하지 않고, 이미 검증된 Node 모듈을 그대로 재사용하기 위해
  신규 CLI 래퍼 `tools/pixelart-gen/pixelate-cli.js`도 함께 신설
  (입력/출력 PNG 경로 + `--gridSize`/`--maxColors`/`--alphaThreshold`
  플래그만 받는 최소 래퍼).
- `launcher.py`를 원본보다 범위를 **의도적으로 좁힘** — 원본은 GPU
  확인→venv→PyTorch(cu128) 설치→ComfyUI 자체를 GitHub에서 다운로드·
  설치→기본 모델(RealVisXL, 약 7GB) 자동 다운로드까지 전부 자동화
  하지만, 사용자는 이미 그 도구로 ComfyUI/venv/PyTorch/모델을 전부
  설치해 둔 상태라 **그걸 통째로 또 설치하면 디스크만 중복되고
  포트 충돌 등 내가 디버그 못 하는 문제가 생길 위험**이 있다고 판단
  (1-5번의 "내가 시험할 수 있는 방식을 골라 만들었다"는 반성과는
  다른 방향의 판단이지만, 같은 교훈 — 근거 없이 범위를 정하지 않고
  이유를 적어 둔다는 원칙은 따름). 그래서 이 버전의 `launcher.py`는
  ①이 도구 전용 venv에 gradio/pillow/requests만 설치 ②기존에 켜져
  있는 ComfyUI(`comfy_alive()`)를 찾아서 재사용 ③없으면 "먼저 켜
  달라"고 안내만 하고 화면은 그대로 띄움(화면 안의 "다시 확인"
  버튼으로 재확인 가능) — ComfyUI 자체의 신규 설치는 이번 범위
  밖. 필요해지면(예: 다른 PC에 이 도구만 따로 깔아야 하는 경우)
  원본의 `ensure_comfyui()`/`ensure_torch()` 등을 그대로 가져와
  추가할 수 있음.

### 1-4. 검증 — 이 샌드박스에서 할 수 있는 것까지 전부, 못 하는 것은 명시

이 세션도 GPU/ComfyUI가 없는 클라우드 샌드박스라(`왜_이렇게_만들었나.txt`
1절과 같은 제약), "연결이 맞다"와 "그림이 좋다"를 똑같이 구분해서 적는다.

**실제로 확인한 것**:
- `python3 -m py_compile`로 전 파일 문법 확인.
- ComfyUI의 HTTP API 모양(`/prompt`·`/history/{id}`·`/view`·
  `/system_stats`·`/object_info/CheckpointLoaderSimple`)만 흉내 낸
  Python `http.server` 목업(순수 루프백, 외부 아웃바운드 아님)으로
  `comfy_client.py`의 `comfy_state()`/`get_checkpoints()`/
  `queue_prompt()`/`wait_for_result()`/`fetch_image_bytes()`를 전부
  실제 호출해 왕복 확인, `workflow.py`의 `build_prompt()`/
  `build_workflow()`(LoRA 재배선 포함) 구조 확인.
- 받은 PNG 바이트를 실제 `tools/pixelart-gen/pixelate-cli.js`(진짜
  `pixelate.js`/`png-encoder.js`)로 변환해 파일이 실제로 만들어지는
  것까지 확인(Node 쪽은 78번 라운드와 같은 방식의 목업 서버 테스트도
  이미 끝나 있음).
- `gradio`를 이 샌드박스에 설치해(버전 6.31.0) `ui.py`를 모듈로 임포트
  → `gr.Blocks()`가 예외 없이 만들어지는지, 실제로 로컬 포트에 띄워
  `GET /`이 200과 함께 "taleforge_graphic" 타이틀을 포함한 HTML을
  돌려주는지, ComfyUI가 꺼져 있을 때 `check_status`/`refresh_checkpoints`/
  `do_preview` 등 화면 콜백 함수들이 예외 없이 친절한 한글 안내문을
  돌려주는지까지 직접 호출해 확인. `do_preview()`→`do_pixelate()`를
  목업 서버로 끝까지 이어 돌려 실제 파일(raw PNG→pixel PNG)이 생성되고
  `history.jsonl`에 기록되는 것도 확인(검증 후 테스트로 생긴 파일은
  삭제, `outputs/` 폴더는 빈 상태로 되돌림).
- `node build.js` 클린 재빌드(11.0MB, `src/` 전혀 안 건드려 git diff
  없음) + `pw_final_regression.js`(`missingFns:[]`/`smokeTestErrors:[]`)
  통과 — 이 라운드가 타일포지 본체에 전혀 영향 없음을 교차 확인.

**못 한 것(사용자 PC에서만 확인 가능)**:
- 진짜 ComfyUI로 실제 그림이 Emberville 스타일에 가깝게 나오는지 —
  체크포인트 자체가 스타일을 가장 크게 좌우하는데, 지금 갖고 계신
  체크포인트(RealVisXL 등)는 포토리얼 인물 전용이라 픽셀아트에
  안 맞을 가능성이 큼(README에 명시).
- 실제 브라우저에서 화면 배치가 보기 좋은지, 1~2분 걸리는 진짜 생성
  동안 "그리는 중..." 상태 문구가 자연스럽게 갱신되는지(목업 서버는
  즉시 응답해서 폴링 루프 자체는 돌았지만 체감 속도는 확인 못 함).
- `get_checkpoints()`/`get_loras()`가 사용자의 실제 ComfyUI
  `/object_info` 응답 형식과 100% 같은 모양인지(ComfyUI 버전에 따라
  달라질 수 있음 — 원본 도구도 이미 같은 엔드포인트를 써 왔으니
  가능성은 높지만 실측은 아님).
- `launcher.py`가 실제 Windows 환경(`py -3.11` 등)에서 venv를 정상
  생성하는지 — 이 샌드박스는 리눅스라 `py` 런처 자체가 없어 그
  분기(`START.bat`)를 실행해 보지 못함, 코드는 원본의 검증된
  `START.bat` 패턴을 그대로 따름.

### 1-5. "왜_이렇게_만들었나.txt"에서 이어받은 교훈 — 이 도구에도 적용

- **말할 때 "확인한 것 / 못 본 것"을 먼저 나누고, "PC에서 처음
  확인하는 것"을 분명히 밝힌다** — README.txt 마지막 섹션과 이
  메모 전체에 그대로 적용(1-4번 구조).
- **근거 없는 값을 마음대로 넣지 않는다** — steps=24/cfg=6.5/
  sampler=dpmpp_2m/scheduler=karras는 SDXL 계열에서 흔히 쓰이는
  무난한 기본값이지 실측으로 고른 "최적값"이 아니라는 걸 분명히 함
  (체감상 안 맞으면 화면의 "고급 설정"에서 바로 조절 가능하게
  설계 — 코드 수정 없이 조정 가능하다는 원본 도구의 원칙도 유지).
- **"최선"/"근본 수정"이라고 말하지 않는다** — 이 메모·README 어디에도
  "완성", "최선" 같은 표현을 쓰지 않고 "코드 경로는 검증했다, 실제
  그림 품질은 사용자 PC에서 처음 확인된다"로 일관되게 적음.

### 1-6. 다음에 할 일(미착수)

- 사용자가 실제 PC에서 `START.bat`을 돌려 ①ComfyUI 연결·체크포인트
  목록이 정상 노출되는지 ②실제 생성 결과가 어떤지 확인 — 그 결과에
  따라 프롬프트 프리셋(`STYLE_BASE`)이나 기본 수치를 조정할 가능성 큼.
- Fable 설계 문서가 나오면, 거기서 정의하는 구체적인 에셋 목록
  (카테고리/크기/이름)에 맞춰 이 도구(또는 이 도구의 ComfyUI 호출
  로직)를 실제 자동 파이프라인에 연결하는 작업이 다음 단계로 예상됨
  (아직 설계 문서 자체가 없어 착수 전).

## 2. 픽셀아트 모델 추천 + 원클릭 다운로드 추가 (2026-10-28, 1번 후속)

### 2-1. 배경

1번 섹션 배포 직후 사용자가 "픽셀아트용 체크포인트 추천해주고 이전에
내가 보내준거에서 봤듯이 눌러서 다운할수있게 해주고 적용도 잘 되게해줘"
로 요청 — `simple ui confirm`의 `downloader.py`(WAN/SVI 모델을 버튼
한 번으로 받는 기능)와 같은 패턴을, 이번엔 픽셀아트 모델용으로 추가해
달라는 뜻.

### 2-2. 모델 조사 — 실제로 존재가 확인된 것만 고름

`WebSearch`로 "pixel art SDXL LoRA/checkpoint" 계열을 조사 — 여러 후보
(nerijs/pixel-art-xl, lizozom/pixel-icon-lora-sdxl, mindlywork/pixel_art_style_v1.0,
aziibpixelmix(civitai SD1.5 체크포인트), Pixel Art Diffusion XL(civitai) 등)
중 **파일 경로(blob URL)까지 검색 결과에 실제로 나온 `nerijs/pixel-art-xl`
(SDXL용 LoRA, `pixel-art-xl.safetensors`, 약 171MB)만 확정 채택** — 나머지는
파일명이 추정에 그쳐(예: lizozom은 diffusers 표준 파일명 미확인, civitai
쪽은 다운로드 URL이 modelVersionId를 알아야 하는데 미확인) 목록에서 뺐다.
`WebFetch`로 huggingface.co API를 직접 두드려 파일 목록을 받으려 했으나
이 샌드박스는 huggingface.co 자체가 DNS로 안 풀려(78/21번 섹션과 동일한
"허용 목록 밖 호스트" 제약) 실패 — `WebSearch`(이 세션과 다른 경로로
동작하는 외부 검색)로만 간접 확인했다.

**방향 결정**: 체크포인트를 통째로 바꾸는 추천 대신 **LoRA를 얹는 쪽을
1순위로 추천** — 다운로드가 훨씬 작고(수백 MB vs 수 GB), 지금 쓰시는
체크포인트를 안 바꾸니 기존 워크플로에 영향이 없고, 8GB VRAM에서 새
체크포인트를 또 얹는 부담도 없다는 이유를 `model_catalog.py` 주석과
README에 명시.

### 2-3. 구현

- `downloader.py` 신설 — `simple ui confirm`의 `downloader.py`(변경
  #149까지 다듬어진 버전, 이어받기+리다이렉트 시 인증 헤더 제거)의
  핵심 `download()` 함수를 거의 그대로 포팅, Wan/SVI 등 이 도구와
  무관한 데이터는 가져오지 않음. 404를 한글 메시지로 바꿔주는 처리만
  추가(원본엔 없던 부분).
- `paths.py` 신설 — ComfyUI의 실제 models 폴더 경로를 설정하는 모듈.
  taleforge_graphic은 ComfyUI를 HTTP로만 대화하고 직접 설치/관리하지
  않으므로(1-3절 설계), 다운로드한 파일을 어디에 저장해야 ComfyUI가
  보는지 알 방법이 없다 — 그래서 `simple ui confirm`의 `paths.py`와
  같은 패턴(환경변수 `COMFYUI_MODELS_DIR` 또는 `models_location.txt`
  파일, 둘 다 있으면 환경변수 우선)으로 사용자가 한 번 설정하게 함.
  Windows 끊긴 드라이브 처리(원본 `paths.py`의 #66 패치)는 이 도구에선
  ComfyUI 자체를 설치하지 않아 직접 해당 없음 — 가져오지 않음.
- `model_catalog.py` 신설 — `PIXEL_ART_MODELS` 리스트(name/url/subdir/
  filename/size_hint/desc), 지금은 nerijs/pixel-art-xl 1건만.
- `ui.py`에 "📦 픽셀아트 모델 받기" 아코디언 추가 — ①models 폴더 설정
  (저장하면 바로 상태 문구 갱신) ②추천 목록 각 항목마다 "받기" 버튼
  (진행률을 제너레이터로 매 0.5초 갱신 — `do_preview()`와 같은 폴링
  패턴) ③"직접 URL로 받기"(추천 목록이 틀렸을 때의 대비책, URL 끝의
  파일명을 자동으로 추출해 저장). **"적용도 잘 되게"** 요청에 맞춰,
  다운로드가 "완료"로 끝나면 `refresh_checkpoints()`/`refresh_loras()`
  를 자동 호출해 체크포인트/LoRA 드롭다운이 받은 직후 바로 선택
  가능하게 연결(ComfyUI의 `/object_info`가 매 요청마다 실제 폴더를
  다시 읽는다는 일반적인 동작 방식에 기댄 것 — 실측은 아님, 아래
  2-4절 "못 한 것" 참고).

### 2-4. 검증

localhost 전용 파일 서버로 `downloader.py`를 실전 시나리오까지 검증
(스크래치패드 임시 스크립트 1개, 실행 후 삭제): ①환경변수로
`models_dir()` 인식 ②정상 다운로드 바이트 일치 ③`.part` 파일을 절반만
만들어두고 이어받기 → 실제 서버가 받은 `Range: bytes=1150000-` 헤더
확인 + 최종 바이트 일치 ④404 응답 시 한글 오류 메시지로 변환되는 것
⑤`ui.py`의 `make_catalog_download_handler()` 제너레이터를 실제
엔드투엔드로 끝까지 돌려 파일이 정확한 경로(`<models>/loras/...`)에
생성되는 것까지 확인. 추가로 models 폴더 미설정 시 다운로드가 안전하게
막히는 것, 전체 Gradio 페이지가 새 섹션을 포함해도 여전히 200으로
정상 서빙되는 것, 테스트 중 생긴 `models_location.txt`가 안 남고
지워진 것 확인. `node build.js`+`pw_final_regression.js` 재확인 통과
(`src/` 무변경).

**못 한 것(사용자 PC 전용)**: `nerijs/pixel-art-xl` URL이 실제로
받아지는지(404 등 오류 가능성 있음, README에 명시) · 받은 뒤 ComfyUI가
재시작 없이 LoRA 드롭다운에 바로 보여주는지(대부분의 ComfyUI 버전이
그렇다고 알려져 있지만 실측 아님 — 안 보이면 ComfyUI를 한 번 새로고침/
재시작해 보라고 README에 안내) · Windows 경로(`C:\...`) 입력이
그대로 잘 동작하는지.

**커밋**: `tools/taleforge_graphic/downloader.py`/`paths.py`/
`model_catalog.py` 신설·`ui.py`(다운로드 섹션 추가)·`README.txt`
갱신·`.gitignore`(`models_location.txt` 추가)·이 메모장(2번 섹션) —
커밋·푸시 예정.

**2번 섹션 완료(코드 경로 검증까지).**

## 3. "탑뷰"/장르 비유를 사용자 승인 없이 코드에 박아 넣은 걸 사용자가
직접 지적 — 전면 제거 (2026-10-28, 2번 후속)

### 3-1. 경위 — 내가 틀렸던 부분을 정확히 적어둔다

이 세션 내내(1~2번 섹션 포함) 나는 "Emberville 레퍼런스 = 탑뷰 픽셀아트,
디아블로×스타듀밸리 톤"이라고 계속 전제하고 작업했다. 그런데 이 전제의
실제 출처를 따져보면: ①세션 시작 시점의 시스템 배경 설명(이전 세션/대화
요약으로 추정, 사용자가 이 대화에서 직접 쓴 말이 아님) ②사용자가 보내준
Emberville 스크린샷 2장을 내가 보고 "이건 위에서 내려다보는 각도구나"라고
**내 나름대로 해석**한 것 — 이 둘뿐이다. **사용자가 이 대화에서 "탑뷰로
해달라"고 직접 요청한 적은 한 번도 없었다.**

사용자가 "탑뷰 각도를 원하지도 않았고, 이건 Opus가 나중에 asset prompt를
요청할 때 쓰는 건데 왜 네가 마음대로 손봤냐"고 직접 질문·지적 — 두 가지를
동시에 짚은 것이었다: ①카메라 각도를 내가 단정한 것 자체가 틀렸고
②더 근본적으로, 이 도구의 진짜 용도(Opus가 나중에 뽑아낼 실제 프롬프트를
그대로 테스트하는 통로)에 내가 내 나름의 "게임 디자인 의견"을 끼워 넣은
것 자체가 이 도구의 성격을 벗어난 월권이었다.

### 3-2. 뭘 고쳤는지

`grep -rniI "탑뷰|top-down|stardew|diablo|emberville"`로 이 폴더와
`tools/pixelart-gen/` 전체를 훑어 실제 코드/사용자 노출 문구에 남아있던
걸 전부 찾아 고쳤다(메모장의 과거 기록은 "무슨 일이 있었는지"를 보존하는
목적이라 그대로 둠, 아래 참고):

- **`workflow.py`**: `STYLE_BASE`에서 `"top-down RPG game asset"`과
  `"Stardew Valley x Diablo art style"`을 삭제 — 색감/조명/질감처럼
  실제 이미지에서 보이는 성질(디더링, 어두운 팔레트+포인트 컬러, 글로우
  조명)만 남김. `CATEGORY_PRESETS`의 `tile`/`monster`/`character`/`scene`
  에서도 `"top-down"` 전부 삭제 — 카메라 각도는 전혀 언급하지 않는 쪽으로
  바꿈.
- **`build_prompt()`에 `use_category_preset`/`use_style_base` 두 매개변수
  신설** — 더 근본적인 수정. 둘 다 끄면 입력한 설명을 **한 글자도 안 건드리고
  그대로** 돌려준다. `ui.py`에 두 체크박스(기본 켜짐)와 "실제로 전송될
  프롬프트 미리보기" 칸을 추가해, 사용자가 지금 뭐가 자동으로 덧붙는지
  항상 눈으로 확인할 수 있고, Opus가 나중에 줄 실제 프롬프트를 그대로
  테스트하고 싶으면 체크박스 두 개만 끄면 된다 — "이 도구는 받은 텍스트를
  그대로 보내는 통로"라는 원래 성격으로 되돌린 것.
- **`ui.py`/`README.txt`의 사용자 노출 설명 문구**에서도 "Emberville
  스타일(탑뷰 픽셀아트...)"라고 단정하던 부분을 전부 빼고, "카메라
  각도·장르는 이 도구가 단정하지 않는다"고 명시적으로 고쳐 적음.

### 3-3. 메모장 자체는 고치지 않은 이유

이 2번/1번 섹션의 과거 서술("탑뷰 스타일로 설계했다" 등)은 그대로 둔다 —
**그게 실제로 있었던 일**(내가 그렇게 판단하고 그렇게 만들었다는 사실
자체)이기 때문이다. 기록을 고쳐서 마치 처음부터 안 그랬던 것처럼 만드는
건 이 프로젝트의 기록 원칙(무슨 일이 있었는지 정직하게 남긴다)에 어긋난다
— 대신 이 3번 섹션에 "그게 왜 잘못이었고 어떻게 고쳤는지"를 새로 추가하는
방식으로 남긴다.

### 3-4. 검증

`python3 -m py_compile`로 전 파일 문법 확인, `workflow.build_prompt()`를
직접 호출해 ①기본값(토글 둘 다 켬)에서 `"top-down"`/`"stardew"`/`"diablo"`
문자열이 결과에 전혀 없는 것 ②토글 둘 다 끄면 입력 문자열이 공백 하나
안 바뀌고 그대로 나오는 것 확인. `gradio`로 `ui.py` 재구동해 `GET /` 200
확인 + 새 체크박스 상태에 따라 `update_prompt_preview()`가 정확히 반응
(전체 조합/raw-passthrough 둘 다)하는 것 직접 호출로 확인. `node build.js`+
`pw_final_regression.js`도 재확인 통과(`src/` 무변경).

**3번 섹션 완료.**
